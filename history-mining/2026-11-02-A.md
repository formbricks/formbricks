# History mining: per-developer harvest (mode A)

Date: 2026-11-02. Window: 2026-05-02 → 2026-11-02. Harvested by an agent from one developer's cloud
sessions and the shared sources. This is the evidence record. The PR that adds it also implements the
candidates that live in this repo, and its description lists what was done and what was left for a human.

## Security first

**SEC-1: there is no check that blocks agent session links from reaching the public repo, and the harness
asks for them.** `AGENTS.md:56` and `.github/pull_request_template.md:15` forbid `claude.ai/code/session_…`
links and `Claude-Session:` trailers. No hook or CI job enforces this. Every cloud session's harness
reminder tells the agent to append both, and this session's reminder does too. Since the rule landed
(formbricks/formbricks#9388, 2026-09-24), **28 of the 477 PR bodies** opened through 2026-11-02 end in a
`_Generated by [Claude Code](…/code/session_<id>)_` footer that links a session. Examples:
formbricks/formbricks#9388 itself, #9419, #9553, #9630, #9713, #9774, #9782. Every one was found by the
checker this proposal adds, run over each body. A history rewrite was also needed to strip trailers from
branch commits (cloud session "Audit log coverage audit", 2026-10-13). Squash merges have kept them out of
`main`'s commit messages so far (0 hits since 2026-05-02). PR and review comments carry the same footer
and were not scanned. I searched Linear for "session link" and "Claude-Session" and found **no
existing ticket**. Candidate 1 proposes the check.

**Security tickets already filed.** These came up during mining and are listed here, not re-filed. I
checked the status myself only for the ones marked ✔; the rest come from the Linear miner.

- ENG-6870 (Triage ✔): saved segments reveal Restricted-survey completers through personal links.
- ENG-6869 (Triage ✔): public response PUT checks `finished` before the write transaction.
- ENG-6834, ENG-6835, ENG-6838 (Triage ✔): Dependabot better-auth advisories ("OAuth state can be used as a
  Magic Link to sign in as another user", "OAuth Proxy lets an attacker sign in as another user").
  These look urgent and are still in Triage.
- ENG-6797 (In Review): unbounded arrays in public response schemas. ENG-4044 (In Review): `/storage`
  upload URLs for draft, closed or archived surveys. ENG-6811 (Triage): restricted-survey leakage.
  ENG-2858 (Backlog): tag-existence oracle. ENG-2591 (Backlog ✔): revoked session still resolves for about
  5 minutes.

**Leads I checked on `main` that are fixed:**

- The storage double-decode authorization bypass (formbricks/formbricks#9412). `getStorageFileNameScope`
  now decodes the same way `getFileStreamForDownload` does, and `apps/web/modules/storage/utils.ts:373`
  records that coupling.
- The legacy org-settings redirect that disclosed the org id is fixed: it now returns 404 for non-members.
- Hub's `publish-sdk.yml` credential exposure (formbricks/hub#127). The `npm-publish` environment's
  protection rules need admin access to verify, so they appear under open questions.

## Candidates, ordered by severity × frequency

### 1. Block agent session links in commits and PR bodies [home: check]

Evidence: 28 PR bodies plus 3 sessions, 2026-08-13 → 2026-11-02.

- 28 PR bodies since the rule landed, for example formbricks/formbricks#9630, #9713, #9774 and #9782: a
  `_Generated by [Claude Code](…)_` footer that links the session.
- cloud session "Audit log coverage audit" (2026-10-13): "Allow a history rewrite and force-push to strip the Claude-Session
  trailers".
- cloud session "Plain chat widget security update" (2026-10-14): a backport PR footer linked a session.
- cloud session "Retro" (2026-10-06): "The harness attribution reminder … says to end commits and PR bodies
  with a claude.ai/code/session\_… link."

Already covered? `AGENTS.md:56` and `pull_request_template.md:15` cover it. It fails because the
harness's own instruction arrives later and more specifically every turn. A prose rule loses that contest
on every run.

Proposed change:

- `.husky/commit-msg` (new): reject a message matching `claude\.ai/code/session_|^Claude-Session:` with
  "Agent session links are banned in this public repo (AGENTS.md). Remove the line and commit again."
- A CI step in `.github/workflows/pr.yml` (or `lint.yml`) runs the same regex over the PR body and every
  commit message in the PR range, and fails the check.

Once both are in place, `AGENTS.md:56` can shrink to one sentence that keeps the reason (the repo is
public and transcripts can hold customer data).

Cost: none always-loaded. `AGENTS.md` gets shorter.
Confidence: high. To settle it, run the regex over the last 100 PR bodies and expect the 2 hits above.

### 2. Every caller-supplied id is resolved inside the caller's tenant [home: CODING_STANDARDS]

Evidence: 26 Linear tickets, 14 fix PRs and about 12 review threads, 2026-05-04 → 2026-11-02.

- ENG-2861: "an id in the request body that nobody checked against the caller's tenant. Twelve shipped
  security fixes on responses".
- formbricks/formbricks#8783: "authorized the `workspaceId` in the URL but loaded the survey by `surveyId`
  alone".
- formbricks/formbricks#8609 r3658669207: "`archivedAt` is mass-assignable on create, and the purge cron
  then deletes the survey."
- formbricks/formbricks#8687 r3721069614: "Nothing constrains the two FKs to the same workspace".
- formbricks/formbricks#8048: the F5 merge (formbricks/formbricks#8017) silently dropped an earlier scope
  fix.

Already covered? `CODING_STANDARDS.md:134` says "Multi-tenancy: All data must be scoped by Organization or
Environment." It failed for three reasons. It names Environment, which v5 renamed to Workspace. It states a
goal rather than the failure shape, which is that the container id is authorized while the nested id is
not. It does not point at the model fix, `apps/web/app/api/v3/responses/lib/reference-manifest.ts`. The
Prisma path instruction in `.coderabbit.yaml` covers composite FKs only.

Proposed change: replace line 134 with:

> - **Tenancy.** An id the caller supplies (URL segment, body field, action input, file key, the target of a
>   `connect`) is resolved by a query filtered on the workspace or organization the caller was authorized
>   for: `where: { id, workspaceId }`, `connect: { id_workspaceId }`. Authorizing the parent is not enough:
>   most cross-tenant fixes shipped this year authorized the URL's workspace and then loaded a nested id
>   alone. Columns the server owns (`archivedAt`, `organizationId`, `createdBy`) are omitted from create
>   and update input. For a write body with several references, the model is the reference manifest in
>   `apps/web/app/api/v3/responses/lib/reference-manifest.ts` (ENG-2861).

Cost: none (it replaces one line). Review-time file.
Confidence: high. To settle it, apply the rule to ENG-6870 and ENG-6811 and check that a reviewer holding
it would have flagged them.

* formbricks/formbricks#8955: the contacts entitlement gated reads; "the write side … never got the gate".
* ENG-6812: "Changing a pending invite's role skips the user-management role floor".

Already covered? No general rule exists. ADR 0010 covers creatives only. The `pr-review` skill hunts

Proposed change: add under "API Design":

> - A gate (sign-up policy, role floor, entitlement, PIN or single-use link, survey status, visibility) is
>   one function that every entry point to the data calls, and the PR names the entry points it checked:

Cost: none always-loaded.

### 4. ADR: Better Auth native endpoints are closed unless wrapped [home: ADR]

Evidence: 8 incidents, 2026-07-09 → 2026-10-22. ENG-2105 (native password-reset bypassed
`PASSWORD_RESET_DISABLED`), ENG-2072 (`EMAIL_AUTH_DISABLED` left credential sign-in live),
formbricks/formbricks#8816, formbricks/formbricks#8821, formbricks/formbricks#9358 (`/update-user`
bypassed the SSO name lock), formbricks/formbricks#9703, ENG-2293, and ENG-3988 ("createUserAction is the
only HTTP path to create a credential account").

Already covered? No. The decision exists only in ENG-2293 and ENG-3988 comments and in `disabledPaths`.

Proposed change: `docs/adr/0017-better-auth-native-endpoints-closed.md` (0016 goes to the renumbered
duplicate; see the delete list):

> # Better Auth's own HTTP endpoints are closed unless we wrap them
>
> `app/api/auth/[...all]/route.ts` mounts `auth.handler` raw, so every endpoint Better Auth ships is public
> the day we upgrade. Endpoints whose policy we own (sign-up, password reset, update-user) are listed in
> `disabledPaths`, and the app reaches them only through our action or route, which applies the policy.
> Policy predicates live once (`modules/auth/lib/signup-policy.ts`), with the `hooks.before` and create
> hooks kept as backstops (ENG-2293, ENG-3988). Consequence: a Better Auth upgrade is reviewed for new
> native endpoints, and each one is either added to `disabledPaths` or wrapped.

Cost: none.
Confidence: medium. To settle it, the auth owner confirms the "closed by default on upgrade" consequence is
the intended policy.

### 5. The check that guards a write runs inside the write's transaction [home: CODING_STANDARDS]

Evidence: 15 review threads across all three windows, plus ENG-6869 and formbricks/formbricks#9613,
2026-05-05 → 2026-11-02.

- formbricks/formbricks#8681 r3681773342: two concurrent requests both see zero users and become the first
  admin.
- formbricks/formbricks#8609 r3636624408: "A restore between those operations permanently deletes a
  restored survey."
- formbricks/formbricks#9666 r4371253216: a stale full-row PATCH undid a concurrent Pause.
- formbricks/formbricks#9412: the audit read the row before the advisory lock.
- formbricks/hub#118 r3689198339: the tenant check ran separately from the records query.

Already covered? Partly. `CODING_STANDARDS.md:60-61` (the `updatedAt` compare-and-set) covers client
races. It does not cover server-side check-then-act.

Proposed change: add under "Database & Prisma Performance":

> - A check that guards a write (a limit, a status, ownership, `finished`, "first user") runs in the same
>   transaction as the write, either on a row read `FOR UPDATE` or as the write's own `WHERE`
>   (`DELETE … WHERE archivedAt IS NOT NULL`). A check read before the transaction is a race. Snapshots
>   for audit and "previous value" diffs are read under that lock too.

Cost: none.
Confidence: high.

### 6. A change to a shared contract is a public API change, and frozen clients count [home: CODING_STANDARDS]

Evidence: 19 incidents, 2026-05-05 → 2026-10-27.

- formbricks/formbricks#7931: cached `segment.filters` in js-core's localStorage was followed by
  formbricks/formbricks#8067, #8322 and #8382.
- formbricks/formbricks#8855: Zapier broke after the v1 response lost `environmentId`.
- formbricks/formbricks#9535: "The 256-level cap is a new 400 on v3 and MCP, undocumented and not declared
  breaking".
- formbricks/formbricks#9786: "Existing write or manage keys silently gain chart and dashboard write".
- formbricks/hub#99: "new `maxLength: 30000` on `value_text`".

Already covered? Partly. The PR template has a breaking-change decision, and `.coderabbit.yaml` warns on
v1 paths. Neither says that a change in a shared wrapper or schema changes every route that uses it, or
that shipped SDKs read the client API frozen.

Proposed change: add under "API Design":

> - A change to a shared schema, the API wrapper, or a key's scope changes every route that uses it: a new
>   400 or 422, a renamed `meta` field or a widened scope gets a breaking-change entry like any route edit.
>   Shipped mobile SDKs, js-core's cached environment state and the Zapier app read `/api/v1` and the client
>   API without updating, so a field there is renamed only by adding the new one beside the old.

Cost: none.
Confidence: medium-high.

### 7. A cap applies to new input on every write path, never to rows already stored [home: CODING_STANDARDS]

Evidence: 6 incidents of stored rows breaking and 4 of asymmetric siblings, 2026-09-18 → 2026-10-27.

- formbricks/formbricks#9423: "These caps also apply when the _stored_ survey is parsed (`prepare.ts:134`
  uses the same document schema)."
- formbricks/formbricks#9786: "some stored queries that render on main now fail" and "adds are uncapped,
  but `PUT` caps at 250".
- formbricks/formbricks#9518: "Keep strict styling validation off unchanged stored values."
- formbricks/formbricks#9252: the legacy 500-key `data` map broke PATCH.
- formbricks/formbricks#9651: "accept survey patches that leave a stored survey's existing issues
  untouched".

Already covered? "Input Limits" (added 2026-11-02) says where a cap goes. It does not say what a cap must

Proposed change: append to "Input Limits":

> - A new or tighter cap applies to what the caller sends, on every write path to that field (create,

>   succeeds.

Cost: none.
Confidence: high.

### 8. A test is done when it goes red on the bug [home: CODING_STANDARDS, wording]

Evidence: 33 review threads across all three windows (16 + 10 + 7) plus ENG-2174, 2026-05-14 → 2026-10-25.
Reviewers include humans, CodeRabbit, kiln-agent and Claude.

- formbricks/formbricks#9252 r4044610737: "Nothing pins `PATCH` to `readWrite`: changing it to `read`
  leaves 77/77 tests green".
- formbricks/formbricks#8648 r3673364556: "the org check turns into a tautology … and every test in the repo
  still passes."
- formbricks/formbricks#8991: "the _schema_ is synthetic, so the assertion … is guaranteed by the shape the
  test itself declares".
- formbricks/formbricks#8041: "A regression to `GET` without `DEL` would still pass."
- ENG-2174: mocked P2002 shapes passed CI after the Prisma 7 upgrade had changed them.

Already covered? Partly. `CODING_STANDARDS.md:181-188` defines `unit (red on main)` and
`unit (mutation)` as PR Coverage words, and `.coderabbit.yaml` says to flag tests that cannot fail. It

Proposed change: add as the first bullet under "Do:" in Testing Guidelines:

> - A test is done when it goes **red**: flip the line it guards (the permission argument, the tenant

>   go red: a synthetic schema in place of the real one, an input already invalid for another reason, a
>   mock of the module under test, or a call-site argument nobody asserts.

Cost: none.
Confidence: medium. To settle it, sample 10 new tests in November PRs and count mutation survivors before
and after.

### 12. Errors are classified where they are raised [home: CODING_STANDARDS]

Evidence: 9 + 5 + 5 review threads, 4 swallowing-catch threads and 12 Linear tickets about malformed input
returning 500, 2026-04-30 → 2026-10-22.

- formbricks/formbricks#8219: "please use `safeParse` here, `parse` would throw … and that could return a
  500".
- formbricks/formbricks#8991 r3861184959: the mapper "catches _every_ `ValidationError` … including ones
  raised after the survey row is already committed".
- formbricks/formbricks#9438: a 429 classified as an auth failure.
- formbricks/formbricks#8371: a `catch` swallowed pool-exhaustion errors, so the retry never ran.
- ENG-3550: "A NULL byte in a v3 list filter or cursor answers 500 instead of 400".

Already covered? No. `docs/development/standards/practices/error-handling.mdx` is published product docs
and is not read at review time.

Proposed change: add a section to `CODING_STANDARDS.md`:

> ## Errors
>
> - Client input is validated (`safeParse`, a guarded decode) before any work, and failures answer 400 or 422. Text bound for Postgres rejects `\u0000`.
> - An error is mapped by where it was raised, not by its class: throw a typed error at the input boundary.
>   A `ValidationError` from a stored row, a 429 from a provider, or a storage failure is a server fault,
>   logged at `error`.
> - A `catch` that continues names what it expects. Infrastructure errors (pool exhaustion, timeouts)
>   propagate to the retry that owns them.

Cost: none.
Confidence: medium-high.
