The **Send email** action sends an email each time a run reaches it: to an address collected in a survey
response, to a workspace member, or, with a [Webhook trigger](/workflows/webhook-trigger), to an address the
payload carries.

<Note>Workflows are part of the Formbricks [Enterprise Edition](/self-hosting/advanced/license).</Note>

## Configure the email

Complete these fields in the step's configuration panel:

| Field        | Configuration                                                                         |
| ------------ | ------------------------------------------------------------------------------------- |
| **Send to**  | Select one recipient source from the linked survey or workspace.                      |
| **From**     | Shows the deployment sender address. This value is read-only in the workflow builder. |
| **Reply to** | Enter one or more addresses that should receive replies.                              |
| **Subject**  | Enter the email subject.                                                              |
| **Body**     | Write the message and insert survey recall values where needed.                       |

The **Send to** options are grouped:

- **Questions**: the verified email address, when email verification is enabled for the survey, an Open Text
  question configured for email input, and the email field of a Contact Info question.
- **Embedded Data**: a field passed in with the response, by a link, a URL parameter or the SDK.
- **Members**: a workspace member, including yourself.
- **Expected payload**: with a Webhook trigger, an address from the payload. See
  [Send to an address from the payload](#send-to-an-address-from-the-payload).

To send to an address collected from a response, the survey needs at least one compatible recipient source, such
as an email question, contact information, email verification, or a hidden field.

### Personalize the body

Type `@` in the **Body** editor to insert recall values from the linked survey. You can recall answers,
variables, and hidden fields to personalize the message for each run. Learn more about the available sources
in [Recall Data](/surveys/general-features/recall).

### Include response data

Turn on **Attach response data** to include the triggering survey response with the email. You can then also
turn on **Include Embedded Data**, which adds the response's Embedded Data: the fields passed in with it and the
ones the survey computed.

<Note>
  In API v3 and MCP, **Include Embedded Data** is `includeEmbeddedData`. Its old name, `includeVariables`, is
  deprecated: it is still accepted, stored and returned as written until Formbricks v7.0.0. Use one name or the
  other in a step, not both.
</Note>

## Send to an address from the payload

A workflow with a [Webhook trigger](/workflows/webhook-trigger) can send its **Send email** action to an address
from the payload, such as the customer in a closed support ticket. Add a link to a survey with Embedded Data, and
each answer is tied to the event that sent the email.

### Example

A helpdesk calls the Webhook Secret URL when a ticket is closed:

```json
{ "customer": { "email": "dana@example.com", "id": "CUST-48213" }, "channel": "phone" }
```

The workflow emails `dana@example.com` a link like
`https://surveys.example.com/s/<surveyId>?customer_id=CUST-48213&channel=phone`. When Dana answers, the response
stores `customer_id` and `channel` as Embedded Data.

### Set up the email

<Steps>
  <Step title="Pick the recipient">
    In **Send to**, type `@` and pick the payload Variable that holds the address, such as
    `payload.customer.email`.
  </Step>

  <Step title="Write a fixed subject and body">
    Write the subject and body as plain text. With a recipient from a Variable, neither can insert Variables or
    survey answers, and response data can't be attached. See [Why the message is fixed](#why-the-message-is-fixed).
  </Step>

  <Step title="Insert the survey link">
    Place the cursor in the body where the link should go and select **Survey link** in the body's toolbar. In
    **Insert survey link**, choose a link survey in the same workspace.
  </Step>

  <Step title="Pass run data to the survey">
    Under **Pass run data to the survey**, the survey's
    [passed-in Embedded Data fields](/surveys/embedded-data/overview#declaring-a-field) are listed, one row each.
    For each field the response should store, type `@` and pick the Variable that fills it, such as
    `@payload.customer.id`. The value can also be text, or text and Variables together. When a Variable's name
    matches the field, the row suggests it: select **Suggested: use …** to fill it in. A survey with no passed-in
    fields says the link carries no run data.
  </Step>

  <Step title="Insert the link">
    Select **Insert link**. The link shows in the body as a **Survey link** chip. To change it later, select
    **Survey link** again: it opens **Edit survey link**, where **Save** keeps your changes and **Remove link**
    takes the link out.
  </Step>
</Steps>

### Why the message is fixed

Whoever calls the Webhook Secret URL chooses the recipient. If they could also choose the text, a leaked URL would
let anyone send any message, links included, from your sender address. So when the recipient comes from a
Variable, the payload decides who gets the email but never what it says. Only the survey link's Embedded Data can
use Variables, and their values are URL-encoded into the link. They can't use an earlier step's output, such as an
HTTP request's response, so data the workflow fetched never goes to an address the caller picked.

Enabling the workflow fails while the subject or body inserts a Variable or a survey answer, while an Embedded Data
value inserts a step's output, or while **Attach response data** is on.

### Survey link rules

- **A link survey in the same workspace.** Enabling fails for any other survey. The survey's status isn't checked,
  so make sure it is published and open while the workflow sends emails.
- **Only declared keys.** A key the survey doesn't declare as a passed-in Embedded Data field is left off the link.
  When a step was set up through the API or MCP with such a key, or the field was removed from the survey later,
  the row says the survey doesn't take that key from its link.
  So are the keys a link survey reads for itself, such as `lang` and `userId`, so a payload can't change how the
  survey behaves.
- **Keys are matched without case,** so the same key can't be used twice with different spelling.
- **Up to 30 Embedded Data rows,** each value at most 2 KB.

### Sending limits

An address from a Variable isn't checked against your workspace members, so it has its own limits:

- **50 emails per hour per workflow.** This limit doesn't change with `EMAIL_RATE_LIMIT_MULTIPLIER`.
- **Your organization's limits** for email to outside addresses also apply. See
  [Email limits](/self-hosting/configuration/rate-limiting#email-limits).

When a limit is reached, or the run's address is empty or not a valid email address, the step and the run fail
at once, without a retry, and run detail shows the reason. An address that isn't valid is named by its Variable,
not by its value.

## Test it

A [Test run](/workflows/test-runs) sends no email: run detail shows the address and, for an address from the
payload, the survey link the email would have used, so you can check both before you enable.
