Workflows automate tasks in response to events in Formbricks. You tell your agent which event should start the workflow, which events qualify, and what Formbricks should do. The agent writes the workflow definition through [MCP](/platform/mcp/overview) or the [v3 API](/api-v3-reference/introduction), and Formbricks runs it.

<Info>
  Workflows are in **Beta**. Expect the feature set to keep moving; we will note breaking changes here.
</Info>

<Note>Workflows are part of the Formbricks [Enterprise Edition](/self-hosting/advanced/license).</Note>

## How Workflows work

<CardGroup cols={2}>
  <Card title="Trigger" icon="bolt">
    The event that starts a workflow. The currently available trigger is **Response completed** for a
    survey linked to the workflow.
  </Card>

  <Card title="Condition or filter" icon="filter">
    A rule that gates execution. You can currently filter completed responses by the ending card the
    respondent reached.
  </Card>

  <Card title="Action" icon="play">
    What the workflow does after its trigger and filter match. The currently available action is **Send email**.
  </Card>

  <Card title="Run" icon="list-check">
    A concrete execution of an enabled workflow. Every run records its overall status and logs for its
    individual steps.
  </Card>
</CardGroup>

For example, a workflow using the currently available trigger and action follows this sequence:

`Response completed trigger` → `optional ending card filter` → `Send email action`

User-authored condition nodes, branching, webhooks, schedules, delays and loops are not available yet.

## Ask your agent

Describe the automation in plain words, for example: *"When someone finishes the onboarding survey through the thank-you ending, email the account owner the answers."* The agent:

1. Reads the survey (`get_survey`) to find the ending cards and the questions that hold the recipient address.
2. Creates the workflow as a draft (`create_workflow`) and checks it with `test_workflow`, a dry run that creates no run and sends nothing.
3. Enables it (`enable_workflow`) once you are happy.

The **Send email** action needs a recipient. The address can come from an email question, the contact info question, a verified email, a hidden field, or a workspace member. The body can recall answers, variables and hidden fields, and can attach the triggering response.

## Statuses

| Status       | Behavior                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Draft**    | Editable and not running. New and unarchived workflows use this status.                                            |
| **Enabled**  | Runs when its configured trigger fires and its conditions match. The definition is read-only until you disable it. |
| **Disabled** | Stops starting new runs and can be edited and enabled again.                                                       |
| **Archived** | Disabled, read-only, and hidden from the default list. It can be unarchived.                                       |

Agents move a workflow between statuses with `enable_workflow`, `disable_workflow`, `archive_workflow` and `unarchive_workflow`, and copy one with `duplicate_workflow`. A copy is a draft and does not inherit the run history. `delete_workflow` is available after a workflow is archived.

<Warning>
  Deleting a workflow permanently removes the workflow and all of its run history. This cannot be undone.
</Warning>

## Monitor runs

`list_workflow_runs` returns the runs across the workspace or of one workflow, and `get_workflow_run` returns one run in detail: its status, start and finish times, attempt number, any run-level error, the trigger payload, and a chronological list of step logs with duration, input, output and errors.

| Run status    | Meaning                                     |
| ------------- | ------------------------------------------- |
| **Queued**    | The run is waiting to start.                |
| **Running**   | The workflow is currently executing.        |
| **Completed** | All required steps finished successfully.   |
| **Failed**    | The workflow could not finish successfully. |
| **Canceled**  | The run stopped before it completed.        |

Each step log has its own status: **Pending**, **Running**, **Succeeded**, **Failed**, or **Skipped**. A failed step includes its error to help you identify the configuration or delivery problem.

## Permissions

| Workspace access    | Available workflow operations                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Read-only**       | List and read workflows and view workspace-wide or workflow-specific runs.                                             |
| **Write or manage** | Create, change, test, enable, disable, archive, unarchive, duplicate and delete workflows, in addition to read access. |

The agent's OAuth scopes are `workflows:read` and `workflows:write`, and access is always bounded by your own workspace role. Enabled and archived definitions are read-only for everyone.

## Self-host Workflows

Self-hosted deployments run Workflows through the shared Redis-backed Job Runner built into the Formbricks web process. Before using Workflows in production, configure Redis and any services required by your actions, such as SMTP for **Send email**.
