description: "What happens to MCP clients and to permission delivery while you roll out the release that adds organization and workspace access for MCP."

---

**Applies to:** the first release after 6.2. This change is on `main` and not in 6.2 or any earlier patch.
Check it if you upgrade with a rolling update, where containers of the previous version keep running while the
new ones start.

## What changes

- Every MCP connection (one user and one MCP client) gets a **grant**: what the user allows that client to do,
  and in which organizations and workspaces. A data migration gives every existing connection a grant with the
  access it had, so existing clients keep working.
- `/api/mcp` refuses a call whose connection has no grant, with `401`. The client's next token refresh then
  ends the connection, and the user connects the client again.
- The permission schema doesn't change. Grants that select organizations or workspaces are written to SpiceDB
  through the AuthZed outbox, with the new outbox target type `mcp_grant`.

## During a rolling upgrade

Two things can happen while containers of the previous version still run. Both stop once every container runs
the new version, and neither needs action unless you see it.

### A client connected during the rollout gets 401

The data migration gives a grant to every connection that exists when it runs. A container of the previous
version doesn't know grants, so a user who approves an MCP client on that container after the migration gets a
connection without one. That client's calls answer `401` until the user connects it again. Its next token
refresh also fails, which sends it back to the consent screen on its own; Allow on a new container writes the
grant.

Ask anyone who connected an MCP client during the rollout and now sees `401` to connect it again.

### A dead-lettered `mcp_grant` event blocks authorization

The database migration adds the `mcp_grant` triggers while containers of the previous version may still be
delivering outbox events. Those don't know the type and dead-letter its events on the spot instead of retrying.
An event queued when a grant loses access (an Edit that removes a workspace, a revoked connection, a deleted
workspace) is a revocation, and a dead-lettered revocation makes every enforced authorization check in the
deployment fail closed until it is replayed. The scheduled audit replays dead letters only after six hours, so
don't wait for it.

You recognise it by:

- requests that should be allowed being denied across the deployment;
- each Formbricks process logging an `authzed_projection_stale` error;
- `formbricks-authzed outbox status` reporting dead letters.

Once every container runs the new version, check what was dead-lettered:

```sql
SELECT "targetType", "lastErrorCode", COUNT(*) FROM "AuthzedProjectionOutbox"
WHERE "deadLetteredAt" IS NOT NULL AND "processedAt" IS NULL GROUP BY 1, 2;
```

Expect `mcp_grant` rows with `authzed_projection_invalid_event`; investigate anything else before replaying,
as described in [AuthZed operations](/self-hosting/configuration/authzed-operations). Then replay and deliver
them:

```bash
formbricks-authzed outbox replay
formbricks-authzed outbox drain
formbricks-authzed upgrade check
```

Expect `status: ready`. Run `replay` only after the rollout has finished: a container of the previous version
would dead-letter the event again. `replay` resets every unresolved dead letter, which is why you check them
first.

From this release on, a container leaves an outbox event of a type it doesn't know pending for a newer
container instead of dead-lettering it, so the next new type can't cause this.

## If something goes wrong

Going back to the previous version leaves the grant tables in place; that version doesn't read them, and MCP
clients get the access their OAuth scopes give, as before. It doesn't know `mcp_grant` outbox events either, so
it dead-letters them, and `replay` can't deliver them. They mean nothing to that version, so once the rollback
has finished, delete them instead:

```sql
DELETE FROM "AuthzedProjectionOutbox" WHERE "targetType" = 'mcp_grant' AND "processedAt" IS NULL;
```

Then run `formbricks-authzed outbox status` and expect no dead letters. When you upgrade again, the permission
preparation projects every grant's selection again.
