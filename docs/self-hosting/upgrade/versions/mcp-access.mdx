**Applies to:** the first release after 6.2. This change is on `main` and not in 6.2 or any earlier patch.
Check it if you upgrade with a rolling update, where containers of the previous version keep running while the
new ones start.

## What changes

- Every MCP connection (one user and one MCP client) gets a **grant**: what the user allows that client to do,
  and in which organizations and workspaces. Two data migrations give every existing connection a grant with the
  access it had, one for connections approved on the consent screen and one for clients registered with
  `skipConsent`, so existing clients keep working.
- Every MCP access token the new version issues names the grant it was issued under, or no grant when its
  connection had none, and `/api/mcp` refuses a token that doesn't name the connection's grant now. Only a
  token issued by the previous version lacks that claim entirely; it is accepted for the rest of its life (at
  most 15 minutes after the upgrade) when it was issued no earlier than its grant was created. That
  comparison reads the clocks of the container that issued the token and of the database, so keep them in
  sync (NTP) during the upgrade.
- `/api/mcp` refuses a call whose connection has no grant, with `401`. The client's next token refresh then
  ends the connection, and the user connects the client again.
- The permission schema changes: it adds the `mcp_grant` definition and the `mcp_reach` permissions that carry
  a grant's organization or workspace selection down to every resource below it. Grants that select
  organizations or workspaces are written to SpiceDB through the AuthZed outbox, with the new outbox target
  type `mcp_grant`.
- New MCP tools `archive_survey` and `restore_survey`, and `list_surveys` can include archived surveys.
  The `delete_survey` MCP tool is deprecated and will be removed in Formbricks 7.0: it works as before
  until then, but move any client, prompt or automation that calls it to `archive_survey`. Archiving does
  not delete: the survey and its responses are kept for at least 30 days and can be restored until
  Formbricks purges them. An automation that needs the data gone at once deletes the survey in the app or
  through the REST API (`DELETE /api/v3/surveys/{surveyId}`).

## Apply the permission schema

Because the schema changes, this isn't a patch upgrade: follow the full upgrade steps for
[Docker](/self-hosting/upgrade/docker) or [Kubernetes](/self-hosting/upgrade/kubernetes), which run
permission preparation from the new image. In a container of the **new** version:

```bash
formbricks-authzed upgrade prepare
formbricks-authzed upgrade check
```

`upgrade prepare` checks that SpiceDB is healthy, applies the release's schema, delivers the outbox and
projects every grant's selection; it reports `status: prepared` or `status: ready`. `upgrade check` changes
nothing and must report `status: ready` and exit `0`. `prepare` blocks on a schema in SpiceDB that isn't the
previous release's: review `formbricks-authzed schema check` and this release's schema changes before passing
`--expected-current-digest <remoteDigest>`, as in [preparing an upgrade](/self-hosting/upgrade/prepare).

Until the new schema is applied, a grant that selects organizations or workspaces reaches nothing in SpiceDB:
its client is denied, never given more. Grants with All access, which every existing connection gets, work
either way.

## During a rolling upgrade

Two things can happen while containers of the previous version still run. Both stop once every container runs
the new version, and neither needs action unless you see it.

### A client connected during the rollout gets 401

The data migration gives a grant to every connection that exists when it runs. A container of the previous
version doesn't know grants, so a user who approves an MCP client on that container after the migration gets a
connection without one. That client's calls answer `401` until the user connects it again. Its next token
refresh also fails, which sends it back to the consent screen on its own; Allow on a new container writes the
grant.

A client registered with `skipConsent` that connects on a container of the previous version during the
rollout gets no grant either. It skips the consent screen, so it never sees one, but the same holds: its next
token refresh is refused, and it has to authorize again, which a new container answers with a grant.

Ask anyone who connected an MCP client during the rollout and now sees `401` to connect it again.

### A dead-lettered `mcp_grant` event blocks authorization

The database migration adds the `mcp_grant` triggers while containers of the previous version may still be
delivering outbox events. Those don't know the type and dead-letter its events on the spot instead of retrying.
An event queued when a grant loses access is a revocation, and a dead-lettered revocation makes every enforced
authorization check in the deployment fail closed until it is replayed. The scheduled audit replays dead
letters only after six hours, so don't wait for it.

Only grants that select organizations or workspaces queue events. Every grant the data migration creates has
All access, so deleting a user, an MCP client or an organization during the rollout queues nothing for them.
The risk is limited to grants made on a new container during the rollout with Only selected organizations or
Only selected workspaces: editing or revoking one, or deleting a workspace or organization it selects.

You recognise it by:

- requests that should be allowed being denied across the deployment;
- each Formbricks process logging an `authzed_projection_stale` error;
- `formbricks-authzed outbox status` reporting dead letters.

Once every container runs the new version, check what was dead-lettered:

```sql
SELECT "targetType", "lastErrorCode", COUNT(*) FROM "AuthzedProjectionOutbox"
WHERE "deadLetteredAt" IS NOT NULL AND "processedAt" IS NULL GROUP BY 1, 2;
```

Expect `mcp_grant` rows with `authzed_projection_invalid_event`; investigate anything else before replaying,
as described in [AuthZed operations](/self-hosting/configuration/authzed-operations). Then replay and deliver
them, running each command in a container of the **new** version:

```bash
formbricks-authzed outbox replay
formbricks-authzed outbox drain
formbricks-authzed upgrade check
```

Expect `status: ready`. Run `replay` only after the rollout has finished, and never from the previous version's
image: its `drain` dead-letters the replayed `mcp_grant` events again on the spot, yet prints
`deadLettered: 0`, because it dead-letters an event of a type it doesn't know while claiming it, before it
counts anything. Trust `upgrade check`
or `outbox status` from the new image, not that count. `replay` resets every unresolved dead letter of a type
the new version delivers, `mcp_grant` included, which is why you check them first.

From this release on, a container leaves an outbox event of a type it doesn't know pending for a newer
container instead of dead-lettering it, so the next new type can't cause this.

## If something goes wrong

Going back to the previous version leaves the grant tables in place; that version doesn't read them, and MCP
clients get the access their OAuth scopes give, as before. It doesn't know `mcp_grant` outbox events either, so
it dead-letters them, and `replay` can't deliver them. The database triggers that queue them stay after a
rollback, so deleting a user, organization or workspace that a grant selects keeps queueing them, and a
dead-lettered one is a revocation that blocks authorization (see above).

Before you roll back, stop the triggers:

```sql
DROP TRIGGER IF EXISTS "authzed_projection_mcp_grant_delete" ON "McpGrant";
DROP TRIGGER IF EXISTS "authzed_projection_mcp_grant_access" ON "McpGrant";
DROP TRIGGER IF EXISTS "authzed_projection_mcp_grant_organization" ON "McpGrantOrganization";
DROP TRIGGER IF EXISTS "authzed_projection_mcp_grant_workspace" ON "McpGrantWorkspace";
```

Once the rollback has finished, delete the events queued before the triggers went, which mean nothing to that
version:

```sql
DELETE FROM "AuthzedProjectionOutbox" WHERE "targetType" = 'mcp_grant' AND "processedAt" IS NULL;
```

Then run `formbricks-authzed outbox status` and expect no dead letters.

Before you upgrade again, create the four triggers again: run the `CREATE TRIGGER` statements in
`packages/database/migration/20261112140000_add_mcp_grant_projection_trigger/migration.sql`. The migration is
already recorded as applied, so the upgrade doesn't run it again. The permission preparation then projects every
grant's selection again.
