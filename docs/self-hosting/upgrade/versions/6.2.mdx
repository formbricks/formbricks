**Upgrade from:** the latest 6.1 patch. Skipping 6.1 is not supported; see [Upgrade paths](/self-hosting/upgrade/paths).
**Downtime:** a maintenance window. Online upgrades from 6.1 are refused. **Applies to:** all editions and setups.

## What changes

- The permission schema changes for the new [Dashboard viewer role](/self-hosting/upgrade/versions/dashboard-viewer), so permission preparation is needed.
- Published surveys are locked, and every question and answer option gets a code during the migration. See [question codes](/self-hosting/upgrade/versions/question-codes).
- Charts and dashboards get an API and MCP tools, and the Cube model files change. See [charts and dashboards API](/self-hosting/upgrade/versions/charts-dashboards).
- Attachment exports build in the background and need a new bucket permission, and four jobs move to dedicated queues. See [attachment exports](/self-hosting/upgrade/versions/attachment-exports).
- The bundled Valkey moves to 9.1.2 on Docker Compose and Helm. One-click keeps the 8.1.9 image from 6.1 until
  you change it by hand; see [Valkey 9](/self-hosting/upgrade/versions/valkey-9).
- Docker setups add Cube and PostgreSQL memory settings by hand.
- Self-hosted audit logging now needs an Enterprise licence that includes audit logs.

## Before you upgrade

| Who | What to do |
| --- | --- |
| Everyone | Plan a maintenance window. Permission preparation needs the current schema digest; see [schema changes](/self-hosting/upgrade/prepare#schema-changes). The migration also backfills question codes and user activity, so allow extra time on large databases. |
| Kubernetes with `upgrade.mode: online` | Set `upgrade.mode: maintenance` for this upgrade. Online mode refuses 6.1 → 6.2. See [Dashboard viewer role](/self-hosting/upgrade/versions/dashboard-viewer). |
| Docker Compose and one-click | Add the Cube query timeout and PostgreSQL shared memory, and use the 6.2 Cube image and model files. See [Cube memory](/self-hosting/upgrade/versions/cube-memory). |
| Bundled Valkey | Back up the Valkey volume before the image changes. See [Valkey 9](/self-hosting/upgrade/versions/valkey-9). |
| Helm with the bundled PostgreSQL | Move any Cube database settings from `cube.envFrom` or the app Secret to `cube.env`. See [Helm and the bundled database](/self-hosting/upgrade/versions/helm-bundled-database). |
| Your own S3 bucket or job consumer | Add `s3:AbortMultipartUpload` and serve the four dedicated queues. See [attachment exports](/self-hosting/upgrade/versions/attachment-exports). |
| API and MCP clients | Check the [integration changes](#integration-changes-requiring-action) below. |
| Audit logging with `AUDIT_LOG_ENABLED=1` | Check that your Enterprise licence includes audit logs. Without it, audit events stop as soon as you upgrade. The 3-day grace period only covers a licence that lapses later. |

## Upgrade

Follow the runbook for your setup: [Kubernetes](/self-hosting/upgrade/kubernetes),
[Docker Compose](/self-hosting/upgrade/docker) or [one-click](/self-hosting/upgrade/one-click).
Because the permission schema changes, permission preparation asks you to confirm the change. See
[schema changes](/self-hosting/upgrade/prepare).

- **One-click:** download `formbricks.sh` from the 6.2 release before you run `./formbricks.sh update`. The update
  stops with a schema drift (exit `2`) until preparation has run, before it stops or migrates anything. It also
  refreshes the Cube model files, rewrites the RustFS setup script and, where Docker supports it, turns on IPv6 for
  the app network (backup: `docker-compose.yml.before-ipv6-network`; opt out with `enable_ipv6: false`).
- **Kubernetes:** existing installs with the bundled Valkey keep their storage labels, so `helm upgrade` doesn't
  need the StatefulSet recreated. Argo CD and other tools that render with `helm template` can't read the live
  labels, so their first sync to 6.2 fails once; see
  [Upgrade fails on the Valkey StatefulSet](/self-hosting/upgrade/kubernetes#valkey-statefulset-forbidden) for the
  one-time step. Wait for all schema and data migrations to finish before you reopen traffic.

## Check it worked

- Users can sign in and see the surveys they should. Owners, managers and members work as before.
- You can submit a survey response, and API keys work for what they're allowed to do.
- Dashboard charts load in the app and through an authorized API or MCP client.
- **Download attachments** on a survey with files sends an email with a download link, and the ZIP downloads.
- Only then invite anyone as a Dashboard viewer.

Also do the [checks after the upgrade](/self-hosting/advanced/upgrade#after-the-upgrade), or run the
[deployment check](/self-hosting/setup/deployment-check).

## If something goes wrong

Keep the maintenance window open. Before you go back to 6.1, give every Dashboard viewer another role, as
described in [Dashboard viewer role](/self-hosting/upgrade/versions/dashboard-viewer#if-something-goes-wrong).
Then restore the app database, Hub data, SpiceDB, the Valkey volume and your configuration from the backup; see
[backup and restore](/self-hosting/operate/backup-restore). Reverting the app image alone doesn't undo the
migrations.

## Integration changes requiring action

6.2 is a minor release, but these changes can affect existing integrations. They were merged before the
[integration compatibility](/self-hosting/advanced/release-maintenance-policy#integration-compatibility)
commitment was adopted, so 6.2 is the one release it names as an exception.

**API**

* **Published surveys are locked.** Changing a question code, answer code, question type or option text, or deleting an option that existed at launch, on a survey that has left draft returns `422` on v3 and MCP, and `400` with `published_survey_locked:` on v1. See [question codes](/self-hosting/upgrade/versions/question-codes)
* **New organization role.** `GET /api/v2/organizations/{organizationId}/users` can return `dashboard_viewer`. A client that checks roles against a fixed list must accept it
* **v2 user updates.** `PATCH /api/v2/organizations/{organizationId}/users` returns `409` and applies nothing when it changes `name` or `isActive` for a user who also belongs to another organization. Change those fields from an organization the user alone belongs to ([#9683](https://github.com/formbricks/formbricks/pull/9683))
* **v3 survey create errors.** A duplicate question ID in one block now names `blocks.N.elements.M.id` with the code `duplicate_identifier`. A create whose after-commit work fails now returns `201` (v3) or `200` (v1) with the saved survey: treat it as created and don't retry ([#9878](https://github.com/formbricks/formbricks/pull/9878))
* **Standard export sheet name.** The Excel file names its sheet `Response Data` instead of `Sheet1`
* **Webhook payloads** gain `dataByQuestionCode` and `outcome`. Existing keys stay

**MCP**

* **Writes to live surveys need confirmation.** `patch_survey`, `edit_survey_blocks`, `set_survey_block_order` and `delete_survey` on a survey that has responses return `428 Confirmation required` unless the call sends `confirm: true`. Show the user the caution text, then resend ([#9919](https://github.com/formbricks/formbricks/pull/9919))
* **New scopes.** Clients with MCP read or write scopes get `dashboards:read` or `dashboards:write`, and users approve them at their next sign-in. See [charts and dashboards API](/self-hosting/upgrade/versions/charts-dashboards)
