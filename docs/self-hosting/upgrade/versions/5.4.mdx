<Note>
  Historical upgrade notes. Check the [maintenance policy](/self-hosting/advanced/release-maintenance-policy)
  for support status. These instructions describe this release, not the current installation defaults.
</Note>

Read the notes for every version you cross. Use the [upgrade checklist](/self-hosting/advanced/upgrade)
to plan backups, service interruption and recovery. Old commands using `latest` or `stable` must be
resolved to the historical target release before use; they must not jump to today's release.

v5.4 carries one application-level breaking change, and it is narrow: it affects **API keys** used against
the Feedback Records API or the MCP server. If you do not use Unify Feedback, or you only reach it through
the UI, there is nothing to do for it. The release adds no new environment variables. It does ship
**seven database migrations**, applied automatically during the upgrade. Six are quick — new columns and
tables, two of them data migrations that run on their own. The seventh builds an index on the `Response`
table, and it is the one that needs planning: it blocks response writes while it builds, unless you build
the index yourself first. Other migrations add indexes too, but only on new or small tables. See
[Database migrations](#database-migrations) before scheduling the upgrade.

v5.4 also upgrades the **Better Auth** authentication core to 1.7. That upgrade needs no manual database
step — every migration is additive and applies automatically, including the backfills over existing rows —
and **your SSO callback URLs do not change**. It carries one narrow exception, and only for custom code: an
MCP access token is now bound to the session that authorized it, so an integration that caches one across
sessions has to fetch a fresh token — see
[MCP access tokens now end with their session](#mcp-access-tokens-now-end-with-their-session).

The bundled Valkey image moves from an amd64-only 8.1.1 image to the native amd64/arm64 Valkey 8.1.9 Alpine
image. Fresh Docker and Helm installations receive it automatically. Existing installations that retain an
older Compose file or explicitly reuse the previous Helm digest need the one-time update below.

### Bundled Cube image update (action required for some deployments)

5.4.5 makes the same Cube change as 6.0.2: the bundled service moves from `cubejs/cube:v1.6.6` to
`ghcr.io/formbricks/cube:1.7.47-2`, and Helm runs it with a read-only root filesystem. Follow
[Bundled Cube image](/self-hosting/upgrade/versions/6.0#bundled-cube-image-action-required-for-some-deployments) with `version=5.4.5`, so the
`cube` service you copy comes from the 5.4.5 Compose file rather than a 6.x one.

### Envoy Gateway 1.8.4 CRD Upgrade

The updated Helm chart replaces Envoy Gateway 1.7.1 and Gateway API 1.4.1 with Envoy Gateway 1.8.4 and Gateway
API 1.5.1. Fresh installations receive the new CRDs automatically. Helm does not update CRDs during an ordinary
upgrade, so existing installations using the bundled controller must apply the matching CRDs before upgrading:

```bash
crd_dir="$(mktemp -d)"
helm pull oci://docker.io/envoyproxy/gateway-crds-helm \
  --version v1.8.4 --untar --untardir "${crd_dir}"
helm template envoy-gateway-crds "${crd_dir}/gateway-crds-helm" \
  --set crds.gatewayAPI.enabled=true \
  --set crds.gatewayAPI.channel=experimental \
  --set crds.envoyGateway.enabled=true \
  | kubectl apply --server-side --force-conflicts -f -
```

`--force-conflicts` transfers the existing CRD fields from Helm's field manager to this explicit CRD upgrade.
Pulling the OCI chart first keeps Helm 4's pull messages out of the manifest pipe. Remove the temporary directory
after the apply succeeds.

The chart does not install Envoy Gateway's cluster-wide safe-upgrade admission policy by default. Enabling
`envoy.crds.gatewayAPI.safeUpgradePolicy.enabled` denies Gateway API CRD versions older than v1.5.0 across the
whole cluster, including CRDs reconciled by unrelated releases. Enable it only after platform review; a chart
rollback does not remove that policy automatically.

If the platform already manages compatible Gateway API CRDs, do not install another Gateway API bundle. Install
only the Envoy Gateway CRDs as described in the [Kubernetes guide](/self-hosting/setup/kubernetes), set
`envoy.crds.enabled=false`, and configure Flux to skip CRD installation and upgrades. Upgrade the CRDs before the
controller and never downgrade them during rollback.

The controller scheduling values also move from the ineffective `envoy.deployment.envoyGateway.pod` path to
`envoy.deployment.pod`. Move any node selectors, tolerations, topology spread constraints, extra volumes, or
pod annotations that you placed under the old path before upgrading.

The parent chart no longer repeats the bundled controller's default port list. The
`envoy.deployment.ports` override remains supported, so existing port overrides need no migration.

### Database migrations

All seven migrations apply automatically during the upgrade. Two want something from you first: one needs
`WEBAPP_URL` set if you use MCP OAuth, and one deserves a step of its own on large instances. So here
is the full list rather than a summary:

| Migration | What it does | Impact |
| --- | --- | --- |
| `add_feedback_source_import_mode` | Adds `FeedbackSource.import_mode`, which controls whether a source's historical import includes partial responses. Existing sources take the `completedOnly` default, which aligns the historical import with the live ingestion path — that path only ever ran on finished responses, while the import used to pull partials too. Records already in Hub are left alone, so this shows up the next time you run an import: set a source to `all` if it should keep importing partial responses. | Instant |
| `add_organization_display_time_zone` | Adds the nullable `Organization.displayTimeZone`, which formats response timestamps in file exports and in the payloads pushed to Google Sheets, Slack and Airtable (Notion is passed a raw date and is unaffected). | Instant |
| `eng_2343_better_auth_17_resource_model` | The Better Auth 1.7 schema: the `oauthResource` tables, resource columns on OAuth tokens and consents, `alg`/`crv` on `jwks`, and `Account.issuer` with its backfill. Details in the Better Auth 1.7 section below. | Additive and fast. The issuer backfill is what keeps password sign-in working on 1.7, so it must not be skipped — it runs on its own, listed here so it is not mistaken for optional |
| `eng_2343_backfill_oauth_resource_links` | Data migration linking existing MCP OAuth clients, refresh tokens and consents to this instance's `${WEBAPP_URL}/api/mcp` resource, so already-registered MCP clients survive the upgrade. It is a no-op only when the instance has no OAuth client at all, which in practice means a fresh install. | **Set `WEBAPP_URL` before upgrading if you use MCP OAuth.** The resource identifier is derived from it, so on an instance that has OAuth clients an unset or unparseable `WEBAPP_URL` fails this migration and stops the upgrade — set it and re-run |
| `add_feedback_source_element_scope` | Adds `FeedbackSource.elementScope`, which controls whether a source picks up survey questions added later. Existing sources keep the current behaviour (`specific`). | Instant |
| `add_response_survey_finished_index` | Adds an index on `Response(surveyId, finished)` so the survey list's response counts are served from the index instead of scanning the table. | **Blocks response writes while it builds, unless you build the index first — see below** |
| `repair_account_issuer` | Data migration rewriting `Account.issuer` rows that were written with a non-canonical value, which locked the affected Google SSO users into a sign-in loop. Idempotent; a no-op when nothing is wrong. | Fast |

<Warning>
  `add_response_survey_finished_index` builds its index with a plain `CREATE INDEX`, which holds a `SHARE`
  lock on `Response` for the whole build: reads keep working, but **survey responses cannot be written until
  the index is built**. `Response` is usually the largest table on an instance. On small instances the build
  takes seconds. If yours holds millions of responses, [build the index before you
  upgrade](#build-the-response-index-before-you-upgrade) so the migration has nothing left to do, or run the
  upgrade in a window where a pause in response collection is acceptable.

  If you leave the build to the migration, neither documented deployment avoids the pause. On Kubernetes the
  chart runs migrations in their own job while the pods already running keep serving traffic, so the
  responses arriving during the build are the ones that block. On Docker Compose the app container does
  **not** wait for `formbricks-migrate` — it has no `depends_on` on that service and skips startup
  migrations itself — so after the documented `docker compose down && docker compose up -d` the two come up
  in parallel: you get downtime while the app boots, and then blocked writes for however much of the index
  build is left once it starts serving. Compose also stops the migration runner after 300 seconds, so a longer
  build ends as a failed migration; see [If a migration fails](/self-hosting/upgrade/troubleshooting#if-a-migration-fails).
</Warning>

#### Build the response index before you upgrade

The migration creates its index only `IF NOT EXISTS`, so an index you build beforehand makes it a no-op. Built
with `CONCURRENTLY`, the index takes longer but never locks out writes, and the instance keeps running v5.3
while it builds. It does add disk and WAL load, so some writes can slow down while it runs. On a large table the
build can take a while, so run it from a session that survives a dropped connection, such as `tmux` or `screen`:

<Tabs>
  <Tab title="One-Click / Docker Compose">
    From the directory that contains your `docker-compose.yml` (`formbricks` for One-Click installs):

    ```bash
    docker compose exec -T postgres psql -U postgres -d formbricks <<'SQL'
    SET statement_timeout = 0;
    SET lock_timeout = 0;
    CREATE INDEX CONCURRENTLY IF NOT EXISTS "Response_surveyId_finished_idx" ON "Response"("surveyId", "finished");
    SELECT indisvalid FROM pg_index WHERE indexrelid = to_regclass('"Response_surveyId_finished_idx"');
    SQL
    ```
  </Tab>
  <Tab title="Kubernetes">
    If you are using the in-cluster PostgreSQL deployed by the Helm chart:

    ```bash
    kubectl exec -i -n formbricks formbricks-postgresql-0 -- psql -U formbricks -d formbricks <<'SQL'
    SET statement_timeout = 0;
    SET lock_timeout = 0;
    CREATE INDEX CONCURRENTLY IF NOT EXISTS "Response_surveyId_finished_idx" ON "Response"("surveyId", "finished");
    SELECT indisvalid FROM pg_index WHERE indexrelid = to_regclass('"Response_surveyId_finished_idx"');
    SQL
    ```

    <Info>
      If your PostgreSQL pod has a different name, run `kubectl get pods -n formbricks` to find it.
    </Info>
  </Tab>
</Tabs>

With an external or managed PostgreSQL, run the same statements with `psql` as the user that owns the Formbricks
tables, connected directly to the primary rather than through a transaction-pooling connection pooler such as
PgBouncer. A pooler can run the `SET` and the `CREATE` on different server connections. Any other SQL client must
run the `CREATE INDEX` statement on its own, outside a transaction, because `CONCURRENTLY` cannot run inside one.

The two `SET` lines keep a timeout configured on the server, the database or your user from cancelling the
build: `lock_timeout` also limits how long the build waits for other transactions to finish. On PostgreSQL 17 or
later, if `SHOW transaction_timeout;` returns anything other than `0`, add `SET transaction_timeout = 0;` before
the `CREATE` line too.

Then read the `indisvalid` result:

- **`t`**: the index is ready. Upgrade as usual; the migration finds the index and skips the build.
- **`f`**: the index exists but is not usable yet. Do not upgrade over it, because the migration would see the
  name, skip the build, and leave `Response` with an index PostgreSQL never uses. See below.
- **No row**: the `CREATE` failed before it started, for example under the wrong user or on a read-only replica.
  Fix the error it printed and run the commands again.
- **No result at all**: `psql` lost its connection, or never got one, before the check ran. Read on under `f`.

An `f`, or no result at all, means the build is still running or stopped part-way. If the `CREATE` printed an
error, it stopped: fix that cause (often a timeout), drop the index as below, and run the commands again. If your
session dropped instead, the build can still be running on the server, so first check, the same way and as the
same user as above:

```sql
SELECT phase, current_locker_pid FROM pg_stat_progress_create_index
WHERE datname = current_database() AND relid = '"Response"'::regclass;
```

While that returns a row, wait for it to finish and check `indisvalid` again. A `waiting for writers` phase is
waiting for transactions that wrote to `Response`. `waiting for old snapshots` waits for every older transaction
in this database that still holds a snapshot, on any table, so a long report or a `pg_dump` backup counts too.
Either way, `current_locker_pid` is the session it waits for, which you can look up in `pg_stat_activity`. If the
query returns nothing, the build has ended: check `indisvalid` again. `t` means it finished after all, so upgrade
as usual. Still `f` means it was interrupted: drop the index the same way, with the same `SET` lines first, since
a concurrent drop waits under `lock_timeout` too:

```sql
SET statement_timeout = 0;
SET lock_timeout = 0;
DROP INDEX CONCURRENTLY IF EXISTS "Response_surveyId_finished_idx";
```

Add `SET transaction_timeout = 0;` here too if you needed it for the build. Then run the commands above again.

An extra index is harmless to v5.3, so building it early needs no rollback plan of its own.

None of the seven constrains a rollback. v5.3 reads none of the new columns and tables, and the two
`NOT NULL` columns added to existing tables both carry a database default, so a v5.3 instance keeps
writing to those tables exactly as before. Rolling the application images / Helm values back to v5.3 is
safe without touching the database.

Coming back **forward** has one catch, and only if accounts were created while you were rolled back.
`Account.issuer` does not exist in v5.3, so any account signed up or linked on that version is written
without one — and both issuer backfills are already recorded as applied, so rolling forward does not
re-run them. Better Auth 1.7 keys accounts on `(issuer, accountId)`, which makes those rows invisible to
password sign-in and password reset. SSO accounts repair themselves on the next successful sign-in;
password accounts have no such path. If anyone signed up during the rollback window, re-run the repair
after rolling forward. This is the statement the `repair_account_issuer` migration runs, and it is
idempotent — it matches the providers v5.4 ships, so if you have since enabled one that is not listed
here, take the current mapping from that migration rather than this copy:

```sql
UPDATE "Account"
SET "issuer" = CASE
  WHEN "provider" = 'credential' THEN 'local:credential'
  WHEN "provider" = 'google' THEN 'https://accounts.google.com'
  ELSE 'local:oauth:' || "provider"
END
WHERE "issuer" IS DISTINCT FROM (
  CASE
    WHEN "provider" = 'credential' THEN 'local:credential'
    WHEN "provider" = 'google' THEN 'https://accounts.google.com'
    ELSE 'local:oauth:' || "provider"
  END
);
```

The old bundled digest selects only `linux/amd64`. The new digest selects the matching native image on
`linux/amd64` and `linux/arm64`, without requiring QEMU or `binfmt`. Valkey 8.1.9 also contains upstream

### Feedback Record Mutations by API Key (action required for some integrations)

A feedback dataset can be assigned to more than one workspace, and the records inside it carry no workspace
of their own. When a dataset is shared that way, a workspace-scoped permission cannot establish which
workspace a given record belongs to. Two rules now follow from that:

- **Deleting a feedback record requires `manage`.** A key with `write` is no longer enough. This brings
  feedback records in line with every other `DELETE` in the API, which has always required `manage`.
- **A key cannot update or delete records in a shared dataset.** If a dataset is assigned to two or more
  workspaces, an API key is refused regardless of its permission level, with a `403` explaining why.

| Operation | Before | After |
| --- | --- | --- |
| `GET`, search, similar, count | `read` | unchanged |
| `POST /api/v3/feedbackRecords` (create) | `write` | unchanged |
| `PATCH /api/v3/feedbackRecords/{id}` | `write` | `write`, **and** the dataset assigned to one workspace |
| `DELETE /api/v3/feedbackRecords/{id}` | `write` | `manage`, **and** the dataset assigned to one workspace |
| `DELETE /api/v3/feedbackRecords?tenant_id=…` | `write` | `manage`, **and** the dataset assigned to one workspace |

The same applies to the MCP tools `update_feedback_record` and `delete_feedback_record` when the client
authenticates with an API key. The required MCP **scope** is unchanged — both remain `feedbackRecords:write`.

<Note>
  **Only API keys are affected.** Users signing in through the UI, OAuth/MCP connections, and SAML/OIDC
  sessions authorize through their organization role instead, which is unchanged: organization owners and
  managers can still update and delete feedback records, including in a shared dataset. Reading, searching
  and creating records are unaffected for every principal.
</Note>

To find out whether any dataset on your instance is shared, and would therefore start refusing API-key
mutations:

```sql
SELECT d.id, d.name, d."organizationId", COUNT(w."workspaceId") AS workspaces
FROM "FeedbackDirectory" d
JOIN "FeedbackDirectoryWorkspace" w ON w."feedbackDirectoryId" = d.id
WHERE d."isArchived" = false
GROUP BY d.id, d.name, d."organizationId"
HAVING COUNT(w."workspaceId") > 1;
```

Most instances return no rows: a workspace is normally assigned a single dataset, so sharing only exists
where an administrator deliberately assigned a second workspace. For any row that does come back, an
integration that mutates records in that dataset has two ways forward — assign the dataset to a single
workspace under **Settings → Organization → Datasets**, or have the integration authenticate as
an organization owner or manager instead of with a workspace-scoped key.

#### What to do before upgrading

1. Run the query above. If it returns rows, decide how each affected integration should proceed.
2. Raise any API key that deletes feedback records from `write` to `manage`.
3. After deploying, smoke test your feedback-record integrations. Two log lines identify an integration
   caught by the new rules — grep for `Feedback record mutation denied` (the MCP path, which names the
   reason) and for `Feedback records gateway authorization denied` (the REST path, which logs
   `verdict: "deny"` alongside the `operation` and `feedbackDirectoryId`).

#### Rollback

This access-rule change itself ships no migration and touches no schema (the release's migrations are
listed [above](#database-migrations)), so rolling the application images / Helm values back to v5.3 undoes
it with nothing to restore. An API key raised to `manage` in step 2 keeps working on v5.3 —
`manage` was always accepted wherever `write` was — so that step does not need reverting either.

### Better Auth 1.7 upgrade (no action required for most instances)

v5.4 upgrades the Better Auth authentication core from the 1.6 line to 1.7, which fixes
[GHSA-p2fr-6hmx-4528](https://github.com/advisories/GHSA-p2fr-6hmx-4528): MCP OAuth access-token audiences
are now bound to the resource a user actually approved during authorization, instead of trusting whatever
the client requested. This is a coupled core upgrade — it touches login, sessions, 2FA, SSO and MCP OAuth —
but for self-hosted instances it needs no manual database step. Every schema change is additive and nullable,
and the required backfills (account identity, existing OAuth clients, refresh tokens, consents) run
automatically during the upgrade — they are the two `eng_2343` entries in the
[Database migrations](#database-migrations) table above.

The migration also adds two nullable columns, `alg` and `crv`, to the `jwks` table that holds your
instance's JWT signing keys. Keys created before the upgrade keep working untouched — Better Auth reads a
null `alg` as the default algorithm — so there is nothing to backfill, but the columns must exist before
the new version mints its next key.

#### AZUREAD_TENANT_ID: set a concrete tenant for full id_token verification

Better Auth 1.7 verifies Microsoft id_tokens against the issuer advertised by the tenant's OpenID
discovery document whenever `AZUREAD_TENANT_ID` names a concrete tenant — a Directory (tenant) ID GUID or
a verified domain. That is strictly stronger than v5.3 and needs no action.

Two of Microsoft's multi-tenant authorities are different. `common` and `organizations` advertise the
literal placeholder `https://login.microsoftonline.com/{tenantid}/v2.0` as their issuer, so verifying
real tokens against it fails every Microsoft sign-in with `?error=unable_to_get_user_info`. Formbricks
therefore handles those two the way it already handles an unset `AZUREAD_TENANT_ID`: sign-in identity
comes from Microsoft's userinfo endpoint over a client-authenticated call (the v5.3 behavior) and
id_tokens are not verified. The authority you configure still applies at sign-in, so `organizations`
keeps restricting sign-in to work/school accounts, and an unset value behaves as `common`. Formbricks
logs a warning at startup when either is set and Microsoft SSO is enabled. To get full id_token
verification, set your Directory (tenant) ID instead.

`consumers` needs no action and is not affected: every personal Microsoft account lives in one
well-known tenant, so that authority advertises a real issuer and keeps full id_token verification.

#### SSO callback URLs are unchanged

Your SSO callback URLs stay exactly as they are:

| Provider | Callback URL | Action required? |
| --- | --- | --- |
| Azure AD / Entra ID | `https://your-domain.com/api/auth/oauth2/callback/azuread` | No |
| Generic OIDC / Keycloak | `https://your-domain.com/api/auth/oauth2/callback/openid` | No |
| SAML (BoxyHQ / Jackson) | `https://your-domain.com/api/auth/oauth2/callback/saml` | No |
| Google / GitHub | `https://your-domain.com/api/auth/callback/{provider}` | No |

Better Auth 1.7 rebuilds its generic-OAuth support on top of the built-in social-provider route, which
would otherwise have moved these three callbacks to `/api/auth/callback/{providerId}` and required you to
register a new redirect URI at your identity provider. OAuth requires redirect URIs to match exactly, so a
path change means editing every provider configuration by hand.

Formbricks pins the callback URL instead, so it no longer follows the authentication library's internal
routing. The URLs above are the ones introduced in v5.2 and they are now a stable part of the Formbricks
API — a future authentication-core upgrade will not move them either.

<Note>
  The table writes `your-domain.com` as your `WEBAPP_URL`, which is correct for a default install. The
  callback is derived from the same auth base URL Better Auth itself uses, not from `WEBAPP_URL`: that is
  `BETTER_AUTH_URL`, or `NEXTAUTH_URL` when only the legacy name is set, falling back to `WEBAPP_URL` when
  neither is. So if either auth URL names a different origin, the callback lives on **that** origin — register
  that URI at your identity provider. Either way it is unchanged by this upgrade.
</Note>

<Note>
  Nothing to do, and nothing to undo. If you added a `/api/auth/callback/{providerId}` redirect URI in
  advance based on an earlier draft of these notes, leaving it registered is harmless — most identity
  providers accept several redirect URIs, and Formbricks simply will not use it.
</Note>

#### MCP access tokens now end with their session

An MCP access token used to stay valid until its own expiry, independently of the session that authorized
it. In 1.7 it is bound to that session: once the session ends — the user signs out, or the session is
revoked — the token is inactive. `/introspect` reports `active: false` for it and
`/api/auth/oauth2/userinfo` rejects it, rather than honouring it until its TTL runs out.

This is upstream hardening, and it is the stricter of the two behaviours: a token that outlives the sign-out
which created it is exactly what a revocation is supposed to stop.

It applies to **access** tokens. A refresh token granted `offline_access` deliberately survives the session
ending, per OIDC Back-Channel Logout 1.0 §2.7, so that long-lived API access can outlive a browser session —
which is what MCP clients rely on. Signing out is therefore not a way to cut a client off permanently.

**No action is required.** MCP clients re-authorize on their own — Claude Code and MCP Inspector both do —
so a user who signs out and back in sees nothing. It is listed here for one case only: a custom integration
that caches a Formbricks MCP access token and reuses it across sessions will start receiving rejections
where it previously succeeded, and should obtain a fresh token instead of treating the cached one as valid
until its expiry.

#### Rollback (Better Auth 1.7)

The `Account.issuer` column and the new `oauthResource`, `oauthClientResource` and `oauthClientAssertion`
tables are additive and nullable, and are not read by v5.3, so rolling the application images / Helm values
back to v5.3 is safe without touching the database. SSO needs no attention in either direction: v5.3 and
v5.4 use the same callback URLs. If accounts are created while you are rolled back, see the
[rollback note above](#database-migrations) before rolling forward — `Account.issuer` is the one value a
v5.3 instance cannot write.
