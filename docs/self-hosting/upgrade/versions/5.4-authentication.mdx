### Better Auth 1.7 upgrade (no action required for most instances)

v5.4 upgrades the Better Auth authentication core from the 1.6 line to 1.7, which fixes
[GHSA-p2fr-6hmx-4528](https://github.com/advisories/GHSA-p2fr-6hmx-4528): MCP OAuth access-token audiences
are now bound to the resource a user actually approved during authorization, instead of trusting whatever
the client requested. This is a coupled core upgrade — it touches login, sessions, 2FA, SSO and MCP OAuth —
but for self-hosted instances it needs no manual database step. Every schema change is additive and nullable,
and the required backfills (account identity, existing OAuth clients, refresh tokens, consents) run
automatically during the upgrade — they are the two `eng_2343` entries in the
[Database migrations](/self-hosting/upgrade/versions/5.4-database#database-migrations) table above.

The migration also adds two nullable columns, `alg` and `crv`, to the `jwks` table that holds your
instance's JWT signing keys. Keys created before the upgrade keep working untouched — Better Auth reads a
null `alg` as the default algorithm — so there is nothing to backfill, but the columns must exist before
the new version mints its next key.

#### AZUREAD_TENANT_ID: set a concrete tenant for full id_token verification

Better Auth 1.7 verifies Microsoft id_tokens against the issuer advertised by the tenant's OpenID
discovery document whenever `AZUREAD_TENANT_ID` names a concrete tenant — a Directory (tenant) ID GUID or
a verified domain. That is strictly stronger than v5.3 and needs no action.

Two of Microsoft's multi-tenant authorities are different. `common` and `organizations` advertise the
literal placeholder `https://login.microsoftonline.com/{tenantid}/v2.0` as their issuer, so verifying
real tokens against it fails every Microsoft sign-in with `?error=unable_to_get_user_info`. Formbricks
therefore handles those two the way it already handles an unset `AZUREAD_TENANT_ID`: sign-in identity
comes from Microsoft's userinfo endpoint over a client-authenticated call (the v5.3 behavior) and
id_tokens are not verified. The authority you configure still applies at sign-in, so `organizations`
keeps restricting sign-in to work/school accounts, and an unset value behaves as `common`. Formbricks
logs a warning at startup when either is set and Microsoft SSO is enabled. To get full id_token
verification, set your Directory (tenant) ID instead.

`consumers` needs no action and is not affected: every personal Microsoft account lives in one
well-known tenant, so that authority advertises a real issuer and keeps full id_token verification.

#### SSO callback URLs are unchanged

Your SSO callback URLs stay exactly as they are:

| Provider | Callback URL | Action required? |
| --- | --- | --- |
| Azure AD / Entra ID | `https://your-domain.com/api/auth/oauth2/callback/azuread` | No |
| Generic OIDC / Keycloak | `https://your-domain.com/api/auth/oauth2/callback/openid` | No |
| SAML (BoxyHQ / Jackson) | `https://your-domain.com/api/auth/oauth2/callback/saml` | No |
| Google / GitHub | `https://your-domain.com/api/auth/callback/{provider}` | No |

Better Auth 1.7 rebuilds its generic-OAuth support on top of the built-in social-provider route, which
would otherwise have moved these three callbacks to `/api/auth/callback/{providerId}` and required you to
register a new redirect URI at your identity provider. OAuth requires redirect URIs to match exactly, so a
path change means editing every provider configuration by hand.

Formbricks pins the callback URL instead, so it no longer follows the authentication library's internal
routing. The URLs above are the ones introduced in v5.2 and they are now a stable part of the Formbricks
API — a future authentication-core upgrade will not move them either.

<Note>
  The table writes `your-domain.com` as your `WEBAPP_URL`, which is correct for a default install. The
  callback is derived from the same auth base URL Better Auth itself uses, not from `WEBAPP_URL`: that is
  `BETTER_AUTH_URL`, or `NEXTAUTH_URL` when only the legacy name is set, falling back to `WEBAPP_URL` when
  neither is. So if either auth URL names a different origin, the callback lives on **that** origin — register
  that URI at your identity provider. Either way it is unchanged by this upgrade.
</Note>

<Note>
  Nothing to do, and nothing to undo. If you added a `/api/auth/callback/{providerId}` redirect URI in
  advance based on an earlier draft of these notes, leaving it registered is harmless — most identity
  providers accept several redirect URIs, and Formbricks simply will not use it.
</Note>

#### MCP access tokens now end with their session

An MCP access token used to stay valid until its own expiry, independently of the session that authorized
it. In 1.7 it is bound to that session: once the session ends — the user signs out, or the session is
revoked — the token is inactive. `/introspect` reports `active: false` for it and
`/api/auth/oauth2/userinfo` rejects it, rather than honouring it until its TTL runs out.

This is upstream hardening, and it is the stricter of the two behaviours: a token that outlives the sign-out
which created it is exactly what a revocation is supposed to stop.

It applies to **access** tokens. A refresh token granted `offline_access` deliberately survives the session
ending, per OIDC Back-Channel Logout 1.0 §2.7, so that long-lived API access can outlive a browser session —
which is what MCP clients rely on. Signing out is therefore not a way to cut a client off permanently.

**No action is required.** MCP clients re-authorize on their own — Claude Code and MCP Inspector both do —
so a user who signs out and back in sees nothing. It is listed here for one case only: a custom integration
that caches a Formbricks MCP access token and reuses it across sessions will start receiving rejections
where it previously succeeded, and should obtain a fresh token instead of treating the cached one as valid
until its expiry.

#### Rollback (Better Auth 1.7)

The `Account.issuer` column and the new `oauthResource`, `oauthClientResource` and `oauthClientAssertion`
tables are additive and nullable, and are not read by v5.3, so rolling the application images / Helm values
back to v5.3 is possible for these application changes without reversing the schema. This does not establish rollback compatibility for Hub or other changed dependencies. SSO needs no attention in either direction: v5.3 and
v5.4 use the same callback URLs. If accounts are created while you are rolled back, see the
[rollback note above](/self-hosting/upgrade/versions/5.4-database#database-migrations) before rolling forward — `Account.issuer` is the one value a
v5.3 instance cannot write.

### Generic OIDC and `issuer_missing`

Better Auth 1.7 checks the authorization response issuer when the provider supplies `iss`; the older
unconditional requirement is removed. This addresses the earlier missing-issuer failure without an
`OIDC_EMAIL_CLAIM` override. Test your provider's existing-user sign-in and account linking on the chosen patch.
The behavior is present in the [5.4.7 provider configuration](https://github.com/formbricks/formbricks/blob/5.4.7/apps/web/modules/ee/sso/lib/better-auth-providers.ts).
