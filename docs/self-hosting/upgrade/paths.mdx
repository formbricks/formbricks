## The rule

Upgrade **one minor version at a time**, and always to the **latest patch** of each minor version.
**Skipping a minor version is not supported.**

For example, from 5.2.1 you upgrade to 5.2.2, then 5.3.5, then the latest 5.4 patch, then the latest 6.0 patch,
then the latest 6.1 patch.

Each minor release is tested as an upgrade from the latest patch of the previous minor. Each patch is
tested from the previous patch. Other routes are not tested, which is why skipping is not supported.

Within one minor version, you can go straight to its latest patch, for example from 6.0.0 to 6.0.6.
Patches are backward compatible, but a security fix can still need an action from you. Check the
**upgrade impact** of each patch you cross in the
[release notes](/platform/changelog).

## At each stop

1. Read the version page in the table, including its **patch actions**.
2. Upgrade with the runbook for your setup: [Kubernetes](/self-hosting/upgrade/kubernetes),
   [Docker Compose](/self-hosting/upgrade/docker) or [one-click](/self-hosting/upgrade/one-click).
3. Check that the upgrade worked, and that all migrations and background jobs finished, before you
   start the next stop.

Minor and major upgrades run in a maintenance window, because they can contain database migrations.

## Pin exact versions

- Set exact version tags, for example `ghcr.io/formbricks/formbricks:6.0.5`. Never use `latest` to
  upgrade: it jumps straight to the newest release and skips your stops.
- Use the Compose file, Cube model files and migration images from the same release as the app. The
  [configuration checklist](/self-hosting/upgrade/configuration) lists every pin to change.
- On Kubernetes, use the chart with the same version as the app: since 4.0, each release publishes its chart
  with the app's version number. If your values override the image tag, set it to the same version.
- Keep your PostgreSQL major version and storage setup. A newer example file for fresh installs is not
  a reason to change them.

## Old versions

Versions outside the [maintenance window](/self-hosting/advanced/release-maintenance-policy) no longer get
fixes. You can still use them as stops on the way to a maintained version. Upgrade through them in one
maintenance plan and don't leave production on them.
