<Note>This only works with an Ubuntu machine, so ensure the underlying OS is verified beforehand!</Note>

If you’re looking to quickly set up a production instance of Formbricks on an Ubuntu server, this guide is for you. Using a convenient shell script, you can install everything—including Docker, Postgres DB, SpiceDB, and an SSL certificate—in just a few steps. The script takes care of all the dependencies and configuration for your server, making the process smooth and simple.

<Note>
  This setup uses **Traefik** as a **reverse proxy**, essential for directing incoming traffic to the correct
  container and enabling secure internet access to Formbricks. Traefik is chosen for its simplicity and
  automatic SSL management via Let’s Encrypt.
</Note>

<Warning>
  The bundled RustFS option in this one-click setup is designed for convenience on a single server. It is a
  good fit for small-scale or low-complexity self-hosted deployments, but it is not the ideal RustFS
  architecture for high-availability or larger production environments. For stricter production requirements,
  use external object storage or run a dedicated RustFS deployment separately from the Formbricks one-click
  stack.
</Warning>

<Note>
  The installer stores generated PostgreSQL, Hub, Cube, and AuthZed credentials in `./formbricks/.env` and
  restricts the file to `0600`. PostgreSQL has a raw password for the database plus a URL-encoded companion
  for connection strings. When bundled RustFS is enabled, its generated credentials are stored there too. Keep
  that file private, include it in your server backup plan, and avoid checking it into source control or
  copying it to shared locations.
</Note>

<Note>
  For better RustFS performance and stability, prefer local SSD or NVMe-backed storage for the host volume
  behind `rustfs-data`. Avoid NFS and other network filesystems for bundled RustFS data, and use XFS on
  dedicated storage disks when you manage the host layout yourself.
</Note>

For other operating systems or a more customized installation, please refer to the advanced installation guide with [Docker](/self-hosting/setup/docker).

### Requirements

- An Ubuntu Virtual Machine with SSH access.

- A custom domain with an **A record** pointing to your server.

- Ports **80** and **443** are open in your VM's Security Group, allowing Traefik to create an SSL certificate.

### Deployment

Run this command in your terminal:

```bash
curl -fsSL https://raw.githubusercontent.com/formbricks/formbricks/stable/docker/formbricks.sh -o formbricks.sh && chmod +x formbricks.sh && ./formbricks.sh install
```

<Info>
  The v6 one-click stack is based on the production Docker Compose file and includes Formbricks Hub and Cube
  as part of the baseline (Cube configuration lives under `formbricks/cube/`). Ensure your generated
  `formbricks/docker-compose.yml` contains a non-empty `HUB_API_KEY` and that `formbricks/.env` contains
  `CUBEJS_API_SECRET`, `AUTHZED_TOKEN`, and `AUTHZED_DATABASE_PASSWORD` before treating the stack as ready.
  The installer generates these values without printing them and restricts `.env` to `0600`. After
  installation, you own the raw `AUTHZED_DATABASE_PASSWORD` credential.
  `AUTHZED_DATABASE_PASSWORD_URL_ENCODED` is only its generated URI-safe representation, not a second
  credential; the installer's hexadecimal value is safe to reuse for both. Rotate both together. `HUB_API_URL`
  should normally stay at `http://hub:8080`. Bundled SpiceDB is installed for every new setup and does not
  require an Enterprise license check.
</Info>

<Note>
  On the initial v6 startup, Formbricks waits for the installer-created database activation receipt before it
  serves traffic. The bounded wait does not call SpiceDB. After startup, the general `/health` endpoint
  remains independent from SpiceDB. The bundled database configuration provides the two concurrent connections
  required by activation; custom `DATABASE_URL` or PgBouncer configurations must provide at least two
  connections in addition to normal application capacity.
</Note>

<Info>
  The v5 one-click Traefik setup also exposes Hub-backed FeedbackRecords through Formbricks at
  `/api/v3/feedbackRecords` and `/v1/feedback-records`. Traefik calls the internal Formbricks gateway auth
  endpoint first, then forwards allowed requests to Hub with the generated `HUB_API_KEY`. Browser callers should
  request short-lived gateway tokens from `/api/v3/gateway/token` with `{ "service": "feedbackRecords" }`.
</Info>

### Script Prompts

During installation, the script will prompt you to provide some details:

- **Overwriting Docker GPG keys:** If Docker's key already exists, choose whether to replace it.

- **Domain name:** Enter the hostname only, without `http://` or `https://`.

- **HTTPS certificate:** Accept the Let's Encrypt setup for a public production deployment.

- **DNS and firewall confirmation:** Confirm the domain points to the server and ports 80 and 443 are open.

- **Certificate email address:** Enter the address that should receive certificate notifications.

- **HSTS:** Choose whether browsers must always use HTTPS. Enabling it is recommended once HTTPS is working.

- **Email service:** Enter `Y` to configure SMTP, or accept the default `N` to continue without outbound email.

```text
File '/etc/apt/keyrings/docker.gpg' exists. Overwrite? (y/N) y
🔗 Please enter your domain name for the SSL certificate (do not include the protocol):
my.hosted.url.com
🔗 Do you want us to set up an HTTPS certificate for you? [Y/n] Y
🔗 Is DNS configured and are ports 80 and 443 open? [Y/n] Y
💡 Please enter your email address for the SSL certificate:
docs@example.com
🔗 Do you want to enforce HTTPS (HSTS)? [Y/n] Y
📧 Do you want to set up the email service? [y/N] N
🎉 All done! Open https://my.hosted.url.com to finish setup.
```

After the script reports completion, visit the domain you entered and finish the Formbricks setup wizard.

The installer writes `FORMBRICKS_IMAGE_REF=ghcr.io/formbricks/formbricks:stable` to `.env`. Formbricks moves
that image alias with the Git `stable` source tag only for the GitHub-latest stable release; prereleases do not
replace it. The `latest` image alias remains on the supported v5 migration line during the v6 upgrade window.
Existing v5 installations use immutable bridge and target digests from the signed v6 bundle during cutover.
The bridge runs the `legacy_bridge` contract, keeping PostgreSQL-backed v5 authorization authoritative while it
prepares SpiceDB. The v6 target runs `spicedb_authoritative` and requires the compatible activation receipt.
Release publication recognizes only declared v5 and v6 policies; an unknown future major does not move
`stable`, `latest`, or version aliases until its upgrade policy is reviewed.

## Update

To update Formbricks for a minor or patch release, first go to the directory that contains your
`formbricks/` folder. Download the current stable updater there, replacing any older `formbricks.sh`, and
then run it:

```bash
curl -fsSL https://raw.githubusercontent.com/formbricks/formbricks/stable/docker/formbricks.sh \
  -o formbricks.sh
chmod +x formbricks.sh
./formbricks.sh update
```

For an existing v5 installation, first download the target v6 release bundle and follow the
[v6 Upgrade Assistant](/self-hosting/advanced/v6-upgrade-assistant). The normal command above deliberately
blocks rather than starting a v6 image without a database-backed activation receipt.

Starting with v5.4, the updater also recognizes the old amd64-only bundled Valkey digest. It backs up your
Compose file, replaces only that exact image reference with the native amd64/arm64 digest, and validates the
result before pulling. An already-updated or custom Valkey image is left unchanged. The named `redis` volume
and its AOF data are preserved.

Existing one-click installations keep the database credentials in their local `docker-compose.yml` or `.env`.
The update command does not regenerate or rotate them.

<Warning>
  Apart from the exact v5.4 Valkey pin migration described above, `./formbricks.sh update` does **not** rewrite
  your existing `formbricks/docker-compose.yml`. For a major migration such as Formbricks 4.x to 5.0, follow
  the [migration guide](/self-hosting/advanced/migration#v5) first, merge the current v5 Compose changes into
  your existing deployment, confirm `HUB_API_KEY` is set, and only then run the update command. If your older
  one-click install also uses bundled MinIO for file uploads, review that storage path separately before the
  first v5 restart; newer self-hosting updates move the bundled object-storage path to RustFS, while external
  S3-compatible storage keeps the same `S3_*` app contract. The v6 updater preserves that customized file and
  adds the release-signed AuthZed services through a permanent Compose overlay. It does not use a boolean
  acknowledgement or accept a bypass of the activation receipt.

The same applies to pinned third-party images. Because the update command only re-pulls what your Compose
file already names, a bundled `rustfs` service stays on whatever version it was installed with — `docker
  compose pull` cannot move a pinned tag. To take a newer RustFS, edit the `image:` line of the `rustfs`
service in `formbricks/docker-compose.yml` to match the version in the [Docker
guide](/self-hosting/setup/docker), then run the update command. Your `rustfs-data` volume is reused as-is;
roll back by restoring the previous `image:` line.

</Warning>

### Add SpiceDB to an Existing One-Click Installation

Back up `formbricks/.env`, `formbricks/docker-compose.yml`, and the PostgreSQL volume. Download and verify all
assets from the target v6 release, then run:

```bash
/absolute/path/to/the/verified-release-bundle/formbricks.sh update \
  --v6-upgrade-bundle /absolute/path/to/the/verified-release-bundle \
  --yes
```

The updater verifies the signed bundle, leaves `docker-compose.yml` unchanged, and installs a permanent
`formbricks-authzed-overlay.yml`. It runs the release bridge, graph preparation, quiesce, activation, candidate
runtime check, and finalization as one receipt-backed operation. A post-activation failure automatically
returns authority and the running application to the exact bridge image.

The wrapper first instructs you to back up both databases. Its required `--yes` flag acknowledges those backups
and the reviewed cutover plan, then delegates both confirmations to the direct assistant. If you call
`formbricks-upgrade-assistant execute` or `resume` yourself, both `--backup-confirmed` and `--yes` are required;
use the exact commands in the [v6 Upgrade Assistant](/self-hosting/advanced/v6-upgrade-assistant).

Keep the overlay, `.formbricks-v6-upgrade-state.json`, both databases, and the recorded bridge image through
the rollback window. Do not use `docker compose down -v`. The automated path supports the bundled PostgreSQL
service; contact support or follow the operator runbook for an external database.

After the rollback window, keep the overlay as part of the installation. For a later v6 release, replace
`FORMBRICKS_IMAGE_REF` in `formbricks/.env` with that release's reviewed immutable image digest and run the
normal `./formbricks.sh update`. The updater detects the overlay and runs database migrations through the
overlaid Formbricks service, so the preserved v5 Compose file does not need a `formbricks-migrate` service.

For upgrades, restoration, schema changes, and relationship repair, follow the canonical
[AuthZed Operations guide](/self-hosting/advanced/authzed-operations).

## Stop

To stop Formbricks, simply run the following command:

```bash
./formbricks.sh stop
```

The script will automatically stop all the Formbricks related containers and brings the entire stack down.

## Restart

To restart Formbricks, simply run the following command:

```bash
./formbricks.sh restart
```

The script will automatically restart all the Formbricks related containers and brings the entire stack up with the previous configuration.

## Cleanup RustFS Init (Optional)

During the one-click setup, a temporary `rustfs-init` service configures RustFS (bucket, policy, service
user). It is idempotent and safe to leave in place; it will do nothing on subsequent starts once the
configuration exists.

If you prefer to remove the `rustfs-init` service and its references after a successful setup, run:

```bash
./formbricks.sh cleanup-rustfs-init
```

`./formbricks.sh cleanup-minio-init` is still available as a backward-compatible alias.

This only removes the init job and its Compose references; it does not delete any data or affect your RustFS
configuration.

## Uninstall

To uninstall Formbricks, simply run the following command, but keep in mind that this will delete all your data!

```bash
./formbricks.sh uninstall
```

The script will automatically stop all the Formbricks related containers, remove the Formbricks directory, and delete the Docker network.

## Debug

If you encounter any issues, you can check the logs of the containers with:

```bash
./formbricks.sh logs
```

## Troubleshooting

If you encounter any issues, consider the following steps:

- **Inbound Rules**: Make sure you have added inbound rules for Port 80 and 443 in your VM's Security Group.

- **A Record**: Verify that you have set up an A record for your domain, pointing to your VM's IP address.

- **Check Docker Instances**: Run `docker ps` to check the status of the Docker instances.

- **Check Formbricks Logs**: Run `cd formbricks && docker compose logs` to check the logs of the Formbricks stack.
