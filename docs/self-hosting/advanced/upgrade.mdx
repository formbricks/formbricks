Every upgrade follows the same five steps. Do them once for each stop on your
[upgrade path](/self-hosting/upgrade/paths).

<Steps>
  <Step title="Find your setup and version">
    | Your setup | How to recognize it | Check your version |
    | --- | --- | --- |
    | Kubernetes | Installed with the Formbricks Helm chart | `helm list -n <namespace>`, then the image tag of the `formbricks` Deployment |
    | Docker Compose | You manage `docker-compose.yml` yourself | `docker compose images formbricks` in your Compose directory |
    | One-click | A `formbricks.sh` script next to a `formbricks/` directory | `cd formbricks && docker compose images formbricks` |

    If the image tag is `latest`, look up the running version in Formbricks under
    **Organization settings → General → Formbricks version**.
  </Step>
  <Step title="Find your next stop">
    Upgrade one minor version at a time, always to its latest patch. Skipping a minor version is not supported.
    The [upgrade paths](/self-hosting/upgrade/paths) table shows your next stop.
  </Step>
  <Step title="Read the version page">
    Open the [version page](/self-hosting/advanced/migration) for your next stop. Its **Before** section lists
    what to prepare, and its **patch actions** list anything a patch needs. The [release notes](/platform/changelog)
    show the upgrade impact of each release.
  </Step>
  <Step title="Back up">
    Take a [backup you can restore](/self-hosting/operate/backup-restore) of the databases, files and configuration.
    For production, we recommend testing the upgrade on a [copy of your installation](/self-hosting/upgrade/rehearse) first.
  </Step>
  <Step title="Upgrade with your runbook">
    <CardGroup cols={3}>
      <Card title="Kubernetes" icon="dharmachakra" href="/self-hosting/upgrade/kubernetes">
        Helm, Argo CD or Flux.
      </Card>
      <Card title="Docker Compose" icon="docker" href="/self-hosting/upgrade/docker">
        A Compose stack you manage yourself.
      </Card>
      <Card title="One-click" icon="rocket" href="/self-hosting/upgrade/one-click">
        Installed with `formbricks.sh`.
      </Card>
    </CardGroup>
    The runbooks cover upgrades **to 6.0 or later**. To upgrade to a 4.x or 5.x version, use the
    [4.x and 5.x procedure](/self-hosting/upgrade/legacy).
  </Step>
</Steps>

## How much work is an upgrade?

| Upgrade type | Example | What to do | Database migrations | Downtime |
| --- | --- | --- | --- | --- |
| Patch | 6.0.0 → 6.0.5 | Check the upgrade impact of each patch you cross. Otherwise update the version and restart. | Normally none. Exceptions are marked **Action required**. | A short restart |
| Minor | 6.0 → 6.1 | Read the version page and run your runbook. | Possible | A maintenance window |
| Major | 5.4 → 6.0 | Read the version page carefully. New components may be required. Test on a copy first. | Yes | A maintenance window |

During a maintenance window, surveys, the API and the admin UI are unavailable, and background jobs pause.
New survey responses can't be submitted until the upgrade is done. On a single server, every upgrade needs
a restart. On Kubernetes, more replicas protect you from node failures, but they don't make database
migrations safe to run while the old version keeps serving traffic.

## After the upgrade

Keep public traffic closed while you check:

- You can sign in, and a user without access to a survey still can't see it.
- An API key works for what it's allowed to do and is refused for anything else.
- You can submit a survey response, and it appears in the results.
- Webhooks and workflows that you rely on still run.
- All migrations and background jobs finished, and the logs show no errors.

Then open the app in a new browser session. If you use a CDN, check that browsers get the new
[survey assets](/self-hosting/configuration/cdn). For a fuller check, run the
[deployment check](/self-hosting/setup/deployment-check) against a test workspace.

Reopen traffic only when these checks pass. Keep your backup until you're sure the upgrade is good.

## If something fails

Keep the maintenance window open and use [troubleshooting](/self-hosting/upgrade/troubleshooting). Going back
to the old image doesn't undo database migrations. If you can't fix the problem, follow
[backup and restore](/self-hosting/operate/backup-restore) to restore the database, files and configuration together.
