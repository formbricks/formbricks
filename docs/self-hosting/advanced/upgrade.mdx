## Before you start

- Record your current version and choose a target from [stable releases](https://github.com/formbricks/formbricks/releases/latest).
  Read the [release notes](/platform/changelog) for every version you cross, including patches.
  Follow the linked actions; missing historical notes do not establish that an upgrade needs no extra steps.
- Upgrade one major at a time, including any intermediate stops in those notes. A supported path is
  distinct from a **tested pair**: only claim the latter when release evidence names both versions.
- Rehearse with a restored copy of your data. Check your integrations and measure the maintenance window.
- Prepare a [recoverable backup](/self-hosting/operate/backup-restore) and retain the current configuration and images.
- Review [components and ownership](/self-hosting/operate/components), including managed dependencies and workers.

Use `stable` source links to find current guidance. For a production change, record the resolved chart
version and image tags or digests in your deployment configuration. A moving `latest` tag can change
between rehearsal, preparation and rollout.

## Service impact

| Surface | During the standard maintenance procedure |
| --- | --- |
| Surveys and respondents | New submissions pause; let in-flight responses finish before closing traffic. |
| API and admin UI | Unavailable until deployment and acceptance checks complete. |
| Background processing | Writers and workers pause; verify pending work resumes afterwards. |

One-click and single-instance deployments require an interruption. Kubernetes replicas improve
availability during node failures, but do not make database changes safe for mixed app versions.
[Online upgrades](/self-hosting/configuration/online-upgrade) remain conditional and under validation.
Use maintenance unless the selected release and topology have a validated alternative.

## After the upgrade

Keep public traffic closed while you check:

- Sign-in, an allowed user, a denied user, a scoped API key and a revoked permission.
- A survey submission, its stored response, and an expected webhook or workflow delivery.
- Permission preparation, running image IDs, worker queues, logs and dashboard queries.

Open a fresh browser session and hard-refresh an old tab. If you use a CDN, verify
[current renderer assets](/self-hosting/configuration/cdn) reach clients.
Resume controllers and traffic only after acceptance. Retain backups until the upgrade is accepted.


Run the [deployment check](/self-hosting/setup/deployment-check) in a dedicated workspace before reopening
traffic. It complements the permission, worker and release-specific checks; skipped checks are not proof of success.

## If something fails

Keep maintenance active and use [troubleshooting](/self-hosting/upgrade/troubleshooting).
Database changes can make an image-only downgrade unsafe. Follow the
[coordinated restore procedure](/self-hosting/operate/backup-restore) when repair is not possible.
