description: "Safely move an existing Formbricks v5 installation to the SpiceDB-authoritative v6 runtime."
icon: "list-check"
---

Formbricks v6 uses SpiceDB for authorization decisions. Existing data must first be projected from Formbricks
PostgreSQL while a release-matched bridge keeps the v5 authorization behavior authoritative. The signed
upgrade assistant provides a read-only preflight for Docker Compose and Helm, and an automated receipt-backed
cutover for Docker Compose, one-click, and Helm installations.

The bridge and candidate are different runtime modes of release-matched Formbricks images:

- A `legacy_bridge` image keeps the PostgreSQL-backed v5 evaluator authoritative while it writes and repairs the
  SpiceDB projection. The signed v6 bundle supplies an immutable bridge digest built for that v6 cutover.
- A `spicedb_authoritative` image is the v6 candidate and release runtime. It starts only after the database
  contains a compatible activation receipt.

Stable v5 releases use `legacy_bridge`; stable v6 releases use `spicedb_authoritative`. Release automation moves
aliases only for explicitly supported major versions. An unknown future major fails closed without moving
`stable`, `latest`, or major/minor aliases until its publication and upgrade policy is reviewed.

Helm upgrades require Helm 3.15 or newer. The assistant validates each permanent-chart revision with a
secret-hidden server-side dry run so the chart can safely reuse generated credentials from the live release.

<Warning>
  Back up the Formbricks PostgreSQL database and the installation directory before executing the upgrade. Do
  not use `docker compose down -v`: the PostgreSQL volume is the source of product and authorization data.
</Warning>

## Download and verify the release bundle

Download these assets from the same [Formbricks v6 release](https://github.com/formbricks/formbricks/releases):

- `formbricks.sh`, `formbricks-upgrade-assistant`, `formbricks-upgrade-manifest.json`
- `formbricks-authzed-overlay.yml`, `authzed-postgres-bootstrap.sh`, `authzed.com_spicedbclusters.yaml`
- `formbricks-<version>.tgz`, `formbricks-upgrade-<version>.tgz` for Helm
- `formbricks-upgrade-checksums.txt`, `formbricks-upgrade-checksums.sigstore.json`

Do not mix releases. Install [cosign](https://docs.sigstore.dev/cosign/system_config/installation/), then verify
the release identity and every downloaded file:

```bash
RELEASE_TAG=6.0.0

cosign verify-blob \
  --bundle formbricks-upgrade-checksums.sigstore.json \
  --certificate-identity \
    "https://github.com/formbricks/formbricks/.github/workflows/publish-v6-upgrade-assistant.yml@refs/tags/${RELEASE_TAG}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  formbricks-upgrade-checksums.txt

sha256sum --check formbricks-upgrade-checksums.txt
chmod 0755 formbricks-upgrade-assistant
chmod 0755 formbricks.sh
```

On macOS, use `shasum -a 256 --check formbricks-upgrade-checksums.txt`. The signed manifest binds the
operation to distinct immutable bridge and target images, their embedded runtime contracts, and the exact
multi-architecture `pgvector/pgvector` and `authzed/spicedb` image digests used during the upgrade. The
assistant rejects mutable or unexpected image references and installs the signed references into the Docker
environment before Compose renders the upgrade overlay.

The one-click `formbricks.sh` wrapper repeats the release-tag-specific Cosign identity check before delegation.
When invoking `formbricks-upgrade-assistant` directly, the assistant verifies Docker asset digests from the
manifest and Helm assets against the supplied checksum set, but it does not establish the Sigstore signer identity
itself. Complete the exact Cosign command above first; neither `--yes` nor `--backup-confirmed` replaces that
verification.

## Run the read-only preflight

Point `--path` to the Compose file, its directory, or the parent of a one-click `formbricks/` directory:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --path ./formbricks
```

If a customized mutable image does not expose its version, supply the version you independently verified:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --path ./formbricks \
  --current-version 5.4.3
```

For Helm, a version override is not a rollback identity. Before running the assistant, pin the current v5
workload with `deployment.image.digest` and complete that ordinary Helm rollout. The assistant blocks a
tag-only source release because its first bridge upgrade could fail before an immutable bridge revision exists;
rolling back a moved tag could otherwise start a different authorization mode. Docker preflight may use the
version override because its rollback keeps the already installed image and then restores the signed bridge.

Preflight renders configuration and reads runtime metadata only. It never pulls images, runs migrations,
changes files, starts SpiceDB, or stops Formbricks. `ready` means the source is supported; it does not mean
the relationship graph has already been built.

The Formbricks `DATABASE_URL` used during activation must permit at least two concurrent connections. If it
contains a `connection_limit`, set it to `2` or higher. When a database proxy such as PgBouncer is in front of
PostgreSQL, reserve at least two usable database connections for each activation process in addition to normal
application capacity. Activation fails closed when the URL declares a lower limit, but neither the assistant nor
the application can prove a proxy's backend capacity.

For Helm, select the release explicitly when the current context contains more than one Formbricks release:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --install-type helm \
  --helm-release formbricks \
  --namespace formbricks
```

Preflight never creates a journal or changes Kubernetes resources. Helm automation requires an existing release
that is visible through `helm list` and whose values can be read with `helm get values`. A Flux `HelmRelease` can
use this path when its Helm release is visible; pause reconciliation before execution and use `--gitops-paused`
only after verifying that pause.

<Warning>
  Argo CD normally renders Helm templates without creating a Helm release, so those installations cannot use
  the automated Helm path. Preflight returns `helm_release_missing`; do not create a fake release or use
  `--gitops-paused` as a bypass. Keep the deployment on v5 and use a support-reviewed migration plan until a
  controller-native upgrade workflow is available.
</Warning>

Run the assistant from a trusted operator workstation with Bash, `jq`, and either `sha256sum` or `shasum`. Docker
upgrades also need Docker Compose; Helm upgrades need Helm 3.15 or newer and `kubectl`. The working directory must
allow creation of mode-`0600` state and log files. A restricted shell, read-only filesystem, or delegated platform
that cannot provide these tools is not eligible for unattended execution.

Helm preflight verifies every direct namespaced operation the assistant performs:

- `get`, `list`, `watch`, `patch`, and `update` on Deployments and HPAs;
- `get`, `list`, and `watch` on ReplicaSets and Pods, plus `get pods/log` and `create pods/exec`; and
- `get`, `list`, `watch`, `create`, `update`, `patch`, and `delete` on Jobs, ConfigMaps, Leases, and Secrets.

Helm's secret-hidden server-side dry runs remain the admission and RBAC check for all rendered chart resources.
Self-hosted mode additionally requires cluster-scoped `get` access to the `SpiceDBCluster` CRD and, only when
`operator.install=true` and the CRD is absent, `create` access. If your platform policy cannot grant the required
access, preflight blocks without mutation; keep v5 serving and use a platform-owner or support-reviewed workflow.

## Execute a Helm upgrade

Use the two verified local chart archives from the same signed release bundle. Do not use an OCI chart or a chart
from another release for this cutover:

```bash
./formbricks-upgrade-assistant execute \
  --manifest ./formbricks-upgrade-manifest.json \
  --checksums ./formbricks-upgrade-checksums.txt \
  --chart ./formbricks-6.0.0.tgz \
  --upgrade-chart ./formbricks-upgrade-6.0.0.tgz \
  --install-type helm \
  --helm-release formbricks \
  --namespace formbricks \
  --state-file ./.formbricks-v6-helm-upgrade.json \
  --backup-confirmed \
  --yes
```

Add `--gitops-paused` only after you have paused a controller detected on the Deployment belonging to the actual
Helm release. If v6 needs AuthZed values that are not already present, pass `--helm-values ./authzed-v6.json`.
This file accepts only `authzed.mode`, `endpoint`, `insecure`, `systemKey`, named `auth` and `datastore` Secret
references, and `operator.install`. Inline secrets, activation controls, cluster overrides, bootstrap jobs,
workload identity, Formbricks database, PostgreSQL, and other topology changes are rejected during the authority
cutover. Apply ordinary chart changes in a separate Helm upgrade afterward. The assistant stores these values in
its mode-`0600` journal; it never modifies the source file or prints Secret values.

The assistant preserves a custom application database from the running v5 Deployment after Helm has rendered any
`tpl` expressions. `DATABASE_URL` must be an explicit, non-optional `secretKeyRef`. When `deployment.envFrom` is
non-empty, `MIGRATE_DATABASE_URL` must also be an explicit, non-optional reference; otherwise a hidden envFrom value
could select a different migration database. If present, both URLs must use keys in the same Secret. An envFrom-only
database, literal URL, ConfigMap reference, or separate migration Secret is ambiguous to the temporary pre-upgrade
Job and blocks before the release changes. Convert that configuration to the explicit Secret references first.

In `selfHosted` mode with `operator.install=true`, the assistant may create a missing compatible
`SpiceDBCluster` CRD. This is create-only: it never patches, replaces, upgrades, or deletes a cluster-scoped CRD.
For a shared or externally managed operator, set `operator.install=false` and have the platform owner install a
compatible, established CRD before the cutover. In `external` mode, also set `operator.install=false`; the
assistant creates neither an operator nor a CRD and uses the existing endpoint and named Secrets.

Execution automatically:

1. Records the original Helm revision, values, replica count, HPA state, and signed asset identities.
2. Deploys the exact bridge digest with release migrations, private SpiceDB, and legacy authorization authority.
3. Installs the temporary coordinator, prepares and audits the graph, and quiesces the application through Helm.
4. Activates the receipt, deploys one exact candidate Pod, and verifies its image, runtime contract, and `/health`.
5. Finalizes, restores the intended replica/HPA and migration policy, verifies the rollout, and uninstalls the
   temporary chart.

`migration.mode=external` is a temporary cutover fence, not the permanent v6 setting. After finalization, the
assistant removes that phase override so the reviewed operator value—or the chart's normal migration Job
default—governs later upgrades.

If the shell, Helm, or Kubernetes client is interrupted, rerun the exact signed inputs with `resume` instead of
starting a new execution:

```bash
./formbricks-upgrade-assistant resume \
  --manifest ./formbricks-upgrade-manifest.json \
  --checksums ./formbricks-upgrade-checksums.txt \
  --chart ./formbricks-6.0.0.tgz \
  --upgrade-chart ./formbricks-upgrade-6.0.0.tgz \
  --install-type helm \
  --helm-release formbricks \
  --namespace formbricks \
  --state-file ./.formbricks-v6-helm-upgrade.json \
  --backup-confirmed \
  --yes
```

If the journal records a GitOps-managed Deployment, keep its controller paused and include `--gitops-paused`
again on every `resume`. The acknowledgment is deliberately not carried across processes.

Resume validates the journal against the signed manifest and chart checksums, then consults the database-backed
activation state. A running v6 bridge or candidate is not treated as completion by itself. Do not delete or edit
the journal, and do not use `helm rollback` on the Formbricks release during the cutover.

## Execute a Docker or one-click upgrade

The automated executor currently supports installations using the bundled `postgres` service. From the
directory that contains the one-click `formbricks/` folder, run the verified updater and bundle:

```bash
/absolute/path/to/the/verified-release-bundle/formbricks.sh update \
  --v6-upgrade-bundle /absolute/path/to/the/verified-release-bundle \
  --yes
```

If version detection was not possible during preflight, add `--current-version 5.4.3`. Standard Docker Compose
operators can invoke the verified assistant directly:

```bash
./formbricks-upgrade-assistant execute \
  --manifest ./formbricks-upgrade-manifest.json \
  --overlay ./formbricks-authzed-overlay.yml \
  --bootstrap-helper ./authzed-postgres-bootstrap.sh \
  --path /absolute/path/to/the/installation \
  --backup-confirmed \
  --yes
```

If execution is interrupted, use the same verified files and installation path with `resume`:

```bash
./formbricks-upgrade-assistant resume \
  --manifest ./formbricks-upgrade-manifest.json \
  --overlay ./formbricks-authzed-overlay.yml \
  --bootstrap-helper ./authzed-postgres-bootstrap.sh \
  --path /absolute/path/to/the/installation \
  --backup-confirmed \
  --yes
```

Direct `execute` and `resume` calls require both acknowledgments. `--backup-confirmed` confirms that the
installation and PostgreSQL backup exist; `--yes` confirms the reviewed cutover plan. The one-click wrapper first
instructs you to back up both databases, then treats its required `--yes` as both acknowledgments when it
delegates to the assistant.

The one-click updater re-verifies the signed checksum set before delegating. Execution then:

1. Preserves the customer-owned `docker-compose.yml` and backs up `.env`.
2. Installs the signed, permanent `formbricks-authzed-overlay.yml` and database bootstrap helper.
3. Generates stable AuthZed secrets, starts private SpiceDB, and runs bridge-compatible migrations.
4. Starts the immutable legacy-authoritative bridge and checks its embedded runtime contract.
5. Applies the canonical schema, drains the outbox, reconciles relationships, and creates a database receipt.
6. Stops only Formbricks, activates the receipt, starts the immutable v6 candidate, checks it, and finalizes.

The base Compose file is never rewritten. Keep the overlay beside it for all later Compose operations:

```bash
docker compose -f docker-compose.yml -f formbricks-authzed-overlay.yml ps
```

The overlay requires `AUTHZED_POSTGRES_BOOTSTRAP_IMAGE_REF` and `SPICEDB_IMAGE_REF`. The assistant writes the
release-reviewed immutable values from the signed manifest; do not replace them with tags during the cutover.

For a later compatible v6 patch release, set `FORMBRICKS_IMAGE_REF` in `.env` to that release's reviewed
immutable image digest and run the normal `./formbricks.sh update`. The updater runs migrations through the
overlaid application service even when the preserved v5 Compose file has no `formbricks-migrate` service. The
startup receipt gate rejects any release whose authorization contract or canonical schema digest differs from
the activated receipt. Do not bypass that failure: a future schema-bearing release requires a supported,
fenced authoritative-to-authoritative refresh procedure before its application Pods can start.

SpiceDB remains private on the Compose network. The executor verifies both the authorization runtime contract and
the container-local `/health` endpoint before finalization. For Docker, it stores sanitized progress in
`.formbricks-v6-upgrade-state.json`. The Helm state file contains the original release values needed for exact
recovery and can therefore contain database URLs, tokens, and other credentials. The state file and detailed local
`formbricks-v6-upgrade.log` both use mode `0600`; keep them private and never attach either file to a support request
without reviewing and redacting it. The assistant never emits credentials in its JSON result.

## Failure and rollback behavior

Before activation, a failure leaves or restores the bridge. After activation, a failed candidate start, runtime
check, application health check, or finalization fences writes, restores the exact signed bridge, switches
database authority back to legacy, and returns a sanitized rollback result. Helm recovery never blindly rolls
back the application release: it selects only the journal-recorded original revision before activation or an
exact, quiesced bridge revision after activation.

Rollback is complete only after the restored bridge reports the `legacy` runtime contract and its container-local
`/health` endpoint succeeds. Until both checks pass, the authority fence remains held and the assistant returns a
manual-recovery result instead of claiming that service was restored. A deliberately dormant Helm source with
zero replicas is the only case with no application process to probe.

If the host or shell stops during the cutover, use `resume` with the same signed inputs. Do not delete the state
file, overlay, bridge image, chart archives, or either database. A manual-recovery result means the journal and
database authority cannot be matched safely; keep Formbricks quiesced and contact support with the command's JSON
result plus only the minimal, manually redacted log excerpts needed for diagnosis. Treat the Helm state file as a
credential-bearing recovery artifact and do not send it to support.

The activation migration builds its outbox ordering index concurrently so a large existing queue does not block
authorization-source writes. A PostgreSQL interruption during that one index build can leave both an invalid
index and a failed Prisma migration record. Keep the bridge or v5 release serving and contact support instead of
marking the migration applied. Recovery must verify and drop only the invalid
`AuthzedProjectionOutbox_sequence_claim_idx`, mark that migration rolled back, and resume the same signed bundle;
the next migration attempt then rebuilds it concurrently.

## Results

Preflight prints one JSON object and exits `0` for `ready` or `not_required`, `2` for a blocked prerequisite,
and `64` for invalid arguments. Execute exits `0` only for `status: "upgraded"`. A blocked or rolled-back
execution exits non-zero. Raw command errors, tokens, database URLs, relationship identifiers, and filesystem
paths are not written to standard output.

Continue with [AuthZed Operations](/self-hosting/advanced/authzed-operations) for database Secret alignment,
backups, validation, and recovery details. The temporary chart's README documents a support-only manual procedure;
the signed assistant is the supported default path.
