The Formbricks v6 upgrade assistant checks whether an existing v5 installation is ready for the AuthZed
upgrade process. It detects one-click, Docker Compose, and Helm installations, validates the signed release
manifest, and prints one sanitized JSON plan.

<Warning>
  The preflight command is read-only. It does not pull images, run migrations, start SpiceDB, change Helm
  values, stop Formbricks, or write an acknowledgement. A `ready` result means the detected installation can
  enter the release-matched upgrade process; it is not proof that the relationship graph is ready for v6.
</Warning>

## Download and verify the assistant

Each Formbricks v6 release includes four assets:

- `formbricks-upgrade-assistant`
- `formbricks-upgrade-manifest.json`
- `formbricks-upgrade-checksums.txt`
- `formbricks-upgrade-checksums.sigstore.json`

Download all four from the same [Formbricks release](https://github.com/formbricks/formbricks/releases). Do not
mix assets from different releases. Install [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)
and verify the signed checksum before executing the assistant:

```bash
cosign verify-blob \
  --bundle formbricks-upgrade-checksums.sigstore.json \
  --certificate-identity-regexp \
    '^https://github\.com/formbricks/formbricks/\.github/workflows/.+@refs/(heads/main|tags/.+)$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  formbricks-upgrade-checksums.txt

sha256sum --check formbricks-upgrade-checksums.txt
chmod 0755 formbricks-upgrade-assistant
```

On macOS, replace the checksum command with `shasum -a 256 --check formbricks-upgrade-checksums.txt`.

The signed manifest binds the plan to two distinct immutable images:

- the v5 bridge image that keeps current authorization authoritative while projection is prepared;
- the v6 target image that uses SpiceDB for authorization decisions.

Both references must use the official `ghcr.io/formbricks/formbricks@sha256:...` form. Mutable tags such as
`latest`, `5.4`, or `6.0.0` are rejected in the release manifest.

## Run Docker or one-click preflight

Run the assistant from the directory containing `docker-compose.yml`, or from the parent directory containing
the one-click `formbricks/` folder:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --path ./formbricks
```

The assistant renders the Compose model without printing it. A Traefik service identifies a one-click install;
other Compose installations are reported as `docker_compose`. It checks that:

- Docker Compose can render the file and contains a Formbricks service;
- a bundled or external PostgreSQL configuration is present;
- the detected v5 version meets the release's minimum supported version.

If a customized Compose file uses a mutable tag such as `latest` and the running image does not expose a
version label, provide the version you verified from the current deployment:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --path ./formbricks \
  --current-version 5.4.3
```

The override affects only the preflight comparison. It does not change the Compose file or running container.
If the one-click installation normally requires `sudo docker`, run the verified assistant through `sudo` or
use the explicit version override; otherwise it cannot inspect the running container for a version label.

## Run Helm preflight

When exactly one Formbricks release is visible, the assistant can detect it:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --install-type helm
```

Select a release explicitly when the current Kubernetes context contains more than one:

```bash
./formbricks-upgrade-assistant preflight \
  --manifest ./formbricks-upgrade-manifest.json \
  --install-type helm \
  --helm-release formbricks \
  --namespace formbricks
```

Helm preflight reads release metadata and user-supplied values. It uses `kubectl auth can-i` to verify that the
current identity can read deployments, create short-lived Jobs, and patch the Formbricks Deployment during the
later cutover. It never runs `helm upgrade`, `kubectl apply`, or another mutating command.

## Interpret the result

The assistant writes exactly one JSON object to standard output. It never includes Compose environment values,
database URLs, AuthZed tokens, filesystem paths, Helm release names, Kubernetes namespaces, or raw command
errors.

```json
{"schemaVersion":1,"status":"ready","mutating":false,"installation":{"type":"one_click","currentVersion":"5.4.3","currentImagePinned":false,"currentImageDigest":null,"databaseMode":"bundled","authzedConfigured":false},"release":{"version":"6.0.0","manifestDigest":"sha256:...","bridgeImageDigest":"sha256:...","targetImageDigest":"sha256:..."},"warningCount":1,"checks":[{"code":"release_manifest_valid","status":"pass"},{"code":"release_images_immutable","status":"pass"},{"code":"docker_compose_available","status":"pass"},{"code":"deployment_config_readable","status":"pass"},{"code":"current_image_mutable","status":"warning"},{"code":"database_configuration_present","status":"pass"},{"code":"source_version_supported","status":"pass"}],"plan":[{"order":1,"phase":"backup","mutating":false,"requiresConfirmation":true},{"order":2,"phase":"prepare_runtime","mutating":true,"requiresConfirmation":true},{"order":3,"phase":"build_relationship_graph","mutating":true,"requiresConfirmation":true},{"order":4,"phase":"fence_and_activate","mutating":true,"requiresConfirmation":true},{"order":5,"phase":"verify","mutating":false,"requiresConfirmation":false},{"order":6,"phase":"remove_temporary_resources","mutating":true,"requiresConfirmation":true}]}
```

| Status         | Exit | Meaning                                                              |
| -------------- | ---- | -------------------------------------------------------------------- |
| `ready`        | `0`  | Supported v5 source and prerequisites were detected                  |
| `not_required` | `0`  | The deployment is already on the target major version                |
| `blocked`      | `2`  | At least one prerequisite failed; no upgrade action was attempted     |
| usage error    | `64` | An option is invalid or a required option value is missing            |

Warnings do not block preflight. For example, a mutable current v5 image is reported as
`current_image_mutable`; the signed bridge and target images remain immutable.

Common blocking codes include:

- `release_manifest_missing`, `release_manifest_invalid`, and `sha256_tool_missing`;
- `installation_not_detected`, `compose_config_invalid`, and `helm_release_ambiguous`;
- `current_version_unknown`, `source_version_unsupported`, and `kubernetes_permissions_insufficient`.

## Continue the upgrade

A `ready` plan deliberately separates inspection from mutation. Before running a release-matched cutover:

1. Back up the Formbricks and SpiceDB datastores and preserve the current configuration.
2. Review the exact bridge and target digests from the signed plan.
3. Follow [AuthZed Operations](/self-hosting/advanced/authzed-operations#upgrade-an-existing-installation-to-v6)
   for graph preparation, the guarded activation, verification, rollback, and temporary-resource cleanup.

Re-run preflight after changing the deployment or downloading a newer release bundle. Never carry a manifest
or image digest from one Formbricks release into another release's upgrade.
