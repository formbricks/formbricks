Applies to any code that sends text to a language model or acts on what comes back: survey generation, chart
generation, enrichments, embeddings, MCP tools. It does not cover using AI tools to write or review our own
code; AI-assisted review is described in [Code reviews](/development/standards/qa/code-reviews).

All calls go through `@formbricks/ai` (`generateObject`, `streamObject`, `generateText`) and, in `apps/web`, through
`lib/ai/service.ts`. Do not import a provider SDK directly.

The rules follow the [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/): prompt injection,
sensitive information disclosure, improper output handling, excessive agency, and unbounded consumption. When in
doubt, check a design against that list.

## Assess the injection risk first

Assume prompt injection will succeed, and design so that it does not matter. Every AI feature gets a short written
assessment in its PR description before it ships, answering four questions:

1. **What untrusted text reaches the model?** Name who can write it: another user, an end respondent, an uploaded
   file, a third-party API.
2. **What can the model see?** List every field in its context. If the prompt were leaked in full, what is exposed?
3. **What can the model do?** List every tool, write, outbound request, and sink its output feeds.
4. **What is the worst case if an attacker controls the text?** Name the data exposed or the action taken, and
   whose it is.

If the worst case crosses a user or tenant boundary, the design is wrong. Fix the design (what the model can see
and do), not the prompt.

Do this twice:

- **While planning**, before the first line of code, so it shapes the design: what goes in the context, which
  tools exist, which limits apply, and which injection fixtures will test it. The plan lists them.
- **After implementing**, against the diff and not the plan. Code drifts: a field gets added to the context, a tool
  gets wider, a limit becomes a setting. Walk the checklist below against the real code, run the injection fixture,
  and put the final assessment in the PR description. Reviewers check it there.

## What to trust

Nothing the model reads or writes is trusted.

- **Input is data, not instructions.** Survey responses, feedback text, uploaded files, imported documents, and
  tool or MCP results are written by people we do not control. A prompt that tells the model to ignore them
  does not make them safe: a guardrail prompt is not a security boundary.
- **Output is untrusted input.** Ask for structured output with a Zod schema, then validate it again on the
  server before use. A schema fixes the shape, not the meaning: it does not make an id, URL, path, or filter safe.
  Never pass model output to SQL, a file path, a URL fetch, a shell, or rendered HTML without the same
  validation you would give a request body.
- **The model has no authority of its own.** A tool the model can call runs as the requesting user. Re-check that
  user's permission and tenant scope on the exact resource inside the tool handler, as you would for an API
  route. Do not give a model a shared service credential, and do not let one call's result widen what the next
  call may do.
- **Side effects need the user's intent.** If content the user did not write (a response, a document) can cause
  a write, send, or delete, require an explicit user action before it runs. Keep the model's action list small and
  read-only by default.

## Sandbox the model

Limit what a hijacked model can reach. The goal is a small blast radius, whatever the text says.

- **Least data in context.** Build the context from queries scoped to the requesting user and workspace, and
  include only the fields the task needs. No secrets, API keys, other tenants' data, or internal ids in a prompt.
- **Least capability.** Read-only by default. Each tool takes the narrowest input it can. A URL the model picks gets
  the same restrictions as a URL a user supplies. Never run model-written code.
- **No sharing across users.** Conversation history, memory, embeddings, and caches are keyed by tenant and user.
  One tenant's text never enters another tenant's context.
- **Safe output rendering.** Render model output as plain text. Markdown or HTML that auto-loads images or links
  can leak the context through the URL.
- **No egress except the provider.** A tool does not send data anywhere else.

## Limits every call needs

Limits are named constants in code, not settings. Set them generously: the aim is to stop a bad or hostile request
from crashing or draining the app, not to restrict normal use. Enforce each at the earliest boundary, test its
edge, and return an error that names the limit. A missing limit is a bug, not a default. The only knob is
`AI_TIMEOUT_MULTIPLIER`, which scales timeouts and lifts no other cap.

| Limit | Why | Where it lives today |
| --- | --- | --- |
| Input size ceiling | Bounds cost and context stuffing | Request schema, checked before the first call (survey generation caps the prompt at 1,200 characters) |
| `maxOutputTokens` | Bounds cost and runaway output; hitting it raises `AIOutputTokenLimitError` | Per call (survey generation uses 8,192) |
| Timeout | A stuck provider must not hold a worker | Per call, through `getAITimeoutMs`, which applies `AI_TIMEOUT_MULTIPLIER` |
| Output shape bounds | Limits what a bad answer can create (blocks, questions, items) | The Zod schema (survey generation: at most 8 blocks, 4 questions per block) |
| Call count and concurrency | Fan-out multiplies cost and provider load | The operation that plans the calls |
| Per-tenant rate limit | One tenant must not spend everyone's quota | `rateLimitConfigs` (survey generation: 10 per minute) |
| Provider quota errors | A 429 from the provider is not a server error | `lib/ai/service.ts` maps it to `TooManyRequestsError` |

Cancellation (the user pressing Stop) is not an incident: pass the abort signal through and do not log it at
error level.

## Performance

- **Smallest model that passes.** Start on a cheap model and move up only when the evals fail.
- **Stable prefix first.** Put fixed instructions and schema before the variable input so provider prompt caching
  applies.
- **No call per row.** Batch or chunk large inputs. Bound parallelism, and never loop one call per record.
- **Off the request path.** If the user does not need to wait, run the work in a worker.
- **Stream long generations** and honour the abort signal.
- **Cache by content hash** where output is deterministic, keyed per tenant.

## Metrics

Every call records input, output, and reasoning tokens (`result.usage`), plus the model, the feature, the
organization, and the outcome: ok, refused, token limit, timeout, provider 429, or schema-invalid. This gives cost
per feature and per organization, alerts on spikes, and proof that a limit holds.

What exists today:

- `@formbricks/ai` returns `usage` on every result and puts the token counts on `AIOutputTokenLimitError`.
- `wrapAiModelWithTracing` sends a per-call trace to PostHog, tagged with the feature, organization, and workspace.
  Privacy mode is on, so no prompt or completion text is sent.
- Tracing does nothing when PostHog is not configured, so instances without it have no token metrics.

A new AI feature adds its name to `AITracingFeature` and passes a tracing context on every call.

## Gating

A feature that sends customer data to a model is off until the organization turns it on. Use the checks in
`lib/ai/service.ts` rather than writing your own: the organization's AI toggle, the license entitlement, and
whether the instance has a provider configured. Each failure has its own error code in `AI_ERROR_CODES`.
Return that code to the client instead of a generic failure.

Feedback and response data should use the self-hosted path where the instance has one, and is never used for
training. A new outbound flow to a model provider is called out in the PR description.

## Logging

Do not log prompts, completions, or the text a user supplied: they hold customer data. Log ids, counts, status
codes, and timings. Tracing goes through `wrapAiModelWithTracing`; check what it records before adding fields.

## Testing

- **Test with small, cheap models.** A feature that works only on a frontier model is fragile and expensive to
  run. A weak model is also the harder test: if validation, bounds, and authorization hold up there, they are doing
  the work rather than the model's judgment.
- **Add injection fixtures.** Put records in the test data whose text tries to instruct the model: ignore the
  task, call a destructive tool, read another tenant's data, or imitate tool output. Run the real flow against a
  cheap model and assert that nothing outside the requesting user's scope was read or changed.
- **Unit tests stub the provider.** Cover the failure paths with a fake: provider 429, refusal, output cut off
  by the token limit, malformed or schema-invalid output, and timeout.
- **Load and failure runs use an OpenAI-compatible stub server** that returns synthetic results with injected
  latency and errors, so a pipeline can be driven at volume without spending anything.

## Checklist for a new AI feature

Use it when planning, and again against the finished diff before the PR is ready.

- The PR description has the four-question injection assessment, with the worst case named.
- The model's context holds only data the requesting user may read, and no secrets.
- Input is bounded before the first call.
- Output is schema-validated on the server, and no unvalidated value reaches a sink.
- Every tool re-checks the requesting user's permission and tenant scope.
- `maxOutputTokens`, timeout, call count, and a per-tenant rate limit are all hardcoded constants.
- Token usage is recorded per call, tagged with the feature and organization.
- Toggle, entitlement, and instance configuration are checked through `lib/ai/service.ts`.
- Nothing customer-authored is logged.
- Tests run on a cheap model and include an injection fixture.
