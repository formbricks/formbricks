## Core Configuration

### oxfmt Config
[oxfmt](https://oxc.rs/docs/guide/usage/formatter) formats the whole repo: TypeScript, JavaScript, JSON, Markdown, YAML, CSS and TOML. Its one config is `oxfmt.config.mts` at the repo root; there are no per-package format configs. `pnpm format` writes, and `pnpm format:check` is the CI gate. The full run takes about two seconds.

Key configurations:
- 110 characters line width
- Double quotes for strings
- ES5 trailing commas
- Always use parentheses for arrow functions
- Imports sorted into fixed groups, with no blank lines between them
- Tailwind classes sorted in `className` and inside `cn()`, `cva()`, `clsx()` and `twMerge()`, against each package's own theme
- `package.json` files keep their key order

oxfmt is pre-1.0, so it is pinned to an exact version and bumped by hand, with the reformat in the same PR. See [ADR 0041](https://github.com/formbricks/formbricks/blob/main/docs/adr/0041-oxfmt-formats-the-repo.md).

### Import Order
oxfmt sorts import statements into these groups:
1. Mocks (`**/__mocks__/**`), so a mock replaces the real module before anything imports it
2. `server-only`
3. Node built-ins and third-party modules
4. Internal `@formbricks/*` modules
5. `~/*` aliases
6. `@/*` aliases
7. Relative imports

The names inside an import's braces are sorted too, case-sensitively (uppercase first). oxfmt cannot do that yet, so oxlint's `sort-imports` rule enforces it, and the pre-commit hook fixes it.

### Locale Files
oxfmt does not sort JSON keys. The keys of every locale file (`apps/web/locales/*.json`, `packages/surveys/locales/*.json`) are kept sorted by `scripts/sort-locale-keys.mjs`, which `pnpm format`, `pnpm format:check` and the pre-commit hook run. Other JSON files keep the order their authors chose.

### TypeScript Config
- Strict TypeScript checking enabled
- Consistent use of `tsconfig.json` extending from `@formbricks/config-typescript`
- Example configuration:

```json
{
  "compilerOptions": {
    "allowImportingTsExtensions": true,
    "isolatedModules": true,
    "noEmit": true,
    "resolveJsonModule": true,
    "strict": true
  },
  "extends": "@formbricks/config-typescript/js-library.json",
  "include": ["src", "package.json"]

```

### Error Handling
Standardized error handling using the ErrorHandler class:

```typescript
export class ErrorHandler {
  private static instance: ErrorHandler | null;
  private handleError: (error: unknown) => void;
  public customized = false;
  public static initialized = false;

  private constructor(errorHandler?: (error: unknown) => void) {
    if (errorHandler) {
      this.handleError = errorHandler;
      this.customized = true;
    } else {
      this.handleError = (error) => {
        Logger.getInstance().error(JSON.stringify(error));
      };
    }
  }

  // ... additional methods
}
```

## Enforcement Tools

### Pre-commit Hooks
Husky runs lint-staged (`.lintstagedrc.mjs`) on every commit. It sorts the keys of staged locale files, formats every staged file with oxfmt, sorts the names inside import braces, and runs `prisma format` on Prisma schemas.

The hook also lints the staged files with oxlint (`scripts/lint-staged-oxlint.mjs`): any lint error fails the commit, and so does a Sonar-parity finding inside the staged lines. `pnpm lint` and the "Run Linters" CI job lint the whole repo.

### oxlint Configuration
[oxlint](https://oxc.rs/docs/guide/usage/linter) lints the whole repo in one run from the root: `pnpm lint:code` (about 15 seconds; add `--quiet` for errors only, or use `pnpm lint:fix` to apply autofixes). Every package and app that lints has its own `oxlint.config.ts`, which composes one of the tiers exported by `@formbricks/config-oxlint`; oxlint checks each file against the nearest config.

| Import | Use for |
| --- | --- |
| `@formbricks/config-oxlint/library` | Node/TypeScript packages (type-aware) |
| `@formbricks/config-oxlint/react` | React packages (react, react-hooks, jsx-a11y; type-aware) |
| `@formbricks/config-oxlint/react-hooks` | React packages that only need the hooks rules |
| `@formbricks/config-oxlint/next` | Next.js applications |

Every tier builds on `@formbricks/config-oxlint/base`, which holds the shared turbo, vitest and unused-vars conventions and the `compose()` helper that merges config fragments. A package with its own rules composes them after the tier:

```typescript
// packages/<pkg>/oxlint.config.ts
import { defineConfig } from "oxlint";
import library from "@formbricks/config-oxlint/library";

export default defineConfig(library);
```

```typescript
// a workspace with its own rules
import { defineConfig } from "oxlint";
import { compose } from "@formbricks/config-oxlint/base";
import library from "@formbricks/config-oxlint/library";

export default defineConfig(
  compose(library, {
    overrides: [{ files: ["**/*.test.ts"], rules: { "typescript/unbound-method": "off" } }],
  })
);
```

Disable a rule on one line with `// oxlint-disable-next-line <rule> -- <reason>`; oxlint also honours existing `eslint-disable` comments.

### Coding Agents
`.claude/settings.json` has a Claude Code hook that formats each file right after Claude Code edits it (`scripts/format-edited-file.mjs`), so agents work on formatted code. Other agents rely on the pre-commit hook and CI.

### Continuous Integration
- `pnpm format:check` runs first in the "Run Linters" job, before the slower lint
- SonarCloud integration for code quality analysis
- Coverage requirements for tests

## VS Code Integration

### Required Extensions
- `oxc.oxc-vscode` - oxfmt formatting and oxlint integration
- `bradlc.vscode-tailwindcss` - Tailwind CSS support

### Recommended Settings
The repo's `.vscode/settings.json` already sets these:

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "oxc.oxc-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.oxc": "always"
  },
  "oxc.typeAware": true,
  "typescript.tsdk": "node_modules/typescript/lib"
}
```

## Best Practices

1. **Consistent Formatting**
   - Let the pre-commit hook format staged files; run `pnpm format` to format everything
   - Use VS Code's format on save feature
   - Follow the established import order

2. **Type Safety**
   - Enable strict TypeScript checks
   - Use explicit type annotations when necessary
   - Avoid using `any` type

3. **Code Organization**
   - Keep files focused and modular
   - Group related functionality
   - Use clear, descriptive names

4. **Documentation**
   - Document complex logic
   - Use JSDoc for public APIs
   - Keep comments current with code changes

These standards ensure consistency across the Formbricks codebase while maintaining high code quality and developer productivity.
