API v3 is the management API the [MCP server](/platform/mcp/overview) is built on, and the one the Formbricks app
is moving onto. It covers surveys, workflows, action classes, contact attribute keys and — the reason most beta
users are here — **Feedback Records**, the normalized store behind Unify Feedback.

Every operation is listed in the sidebar of this section. This page covers what is not obvious from the
operation pages.

## Authentication

Create a management API key — **API Keys** in the organization dropdown of the breadcrumbs, see
[Generate API key](/api-reference/generate-key) — and send it in the `x-api-key` header (an
`Authorization: Bearer <key>` header carrying the same key is also accepted). Keys carry per-workspace
permissions — `read`, `write` or `manage` — and every operation states which one it needs.

```bash
curl "https://app.formbricks.com/api/v3/surveys?workspaceId=<workspaceId>" \
  -H "x-api-key: $FORMBRICKS_API_KEY"
```

Send credentialed requests over **HTTPS only** — an API key in `x-api-key` crosses the wire in cleartext
otherwise. Operations also accept a signed-in browser session, which is how the Formbricks app itself calls
them; the operation pages document the API-key contract.

### Self-hosted instances

Substitute your own origin. Every v3 operation is served by the Formbricks application, so there is nothing
to route or enable — earlier releases needed the API gateway for Feedback Records, and no longer do.

Feedback Records additionally need the feedback store reachable, since that is where the records live:

- **One-click Docker** — configured by the installer.
- **Kubernetes / Helm** — the chart deploys the store by default (`hub.enabled`); to use one you already run,
  disable it and point `HUB_API_URL` and `HUB_API_KEY` at yours.
- **Formbricks Cloud** — ready to use.

The organization also has to hold the Unify Feedback entitlement; without it every feedback operation answers
`403`.

## Feedback Records

A [Feedback Record](/unify-feedback/feedback-records) is one piece of feedback in a normalized shape, stored in
a [Feedback Dataset](/unify-feedback/feedback-datasets). Nine operations under `/api/v3/feedback-records` and
`/api/v3/feedback-datasets` let you list, filter, count, search, create, correct and delete them.

They follow the same conventions as the rest of v3 — camelCase members and enum values, `{data}` and
`{data, meta}` envelopes, `filter[member][op]` filters, RFC 9457 problem responses — so most of what used to
be worth explaining here no longer is. What is left is the part that is specific to feedback.

### Finding a dataset id

Every operation is scoped by `workspaceId`. `datasetId` is optional: a workspace reaches at most one active
dataset, so `workspaceId` alone normally resolves it, and you only need to name a dataset when a workspace
reaches more than one.

`GET /api/v3/feedback-datasets?workspaceId=<workspaceId>` lists the ids. The dataset id is not shown anywhere
in the app, so this is the way to find it.

### Ids cannot be probed

A dataset or record you have no permission for answers **403**, not 404 — and identically to one that does not
exist, so a refusal never tells you whether an id is real. There is no `404` anywhere on this surface. A record
deleted while you were editing it answers `403` too, for the same reason.

### Semantic search needs an embedding model

`POST /api/v3/feedback-records/search/semantic` and `GET /api/v3/feedback-records/{feedbackRecordId}/similar`
compare embeddings, which are computed asynchronously after a record is stored. Two answers are specific to
them:

- **409** — the record exists but has no embedding yet. Retry: embedding is queued, so how long it takes
  depends on how much is queued ahead of it.
- **503** — the instance has no embedding model configured at all, so neither operation can ever work. On
  self-hosted, that is `EMBEDDING_PROVIDER` and `EMBEDDING_MODEL` on the feedback store.

### Permissions

| Operations | API key permission on a workspace the dataset is assigned to |
| ------------------------------------------------------- | ----------- |
| List, count, get, list datasets, semantic search, similar | `read` |
| Create, update | `write` |
| Delete | `manage` |

An API key may **update or delete** only in a dataset assigned to exactly one workspace. On a shared dataset no
workspace permission can say whose records they are, so those calls answer `403`; reading and creating stay
allowed.

### Example

```bash
# The 20 most recent negative text answers in a workspace's dataset
curl -G "https://app.formbricks.com/api/v3/feedback-records" \
  -H "x-api-key: $FORMBRICKS_API_KEY" \
  --data-urlencode "workspaceId=<workspaceId>" \
  --data-urlencode "filter[fieldType][in]=text" \
  --data-urlencode "filter[sentiment][in]=negative" \
  --data-urlencode "filter[sentiment][in]=veryNegative" \
  --data-urlencode "limit=20"
```

Repeat a filter to OR its values, as `filter[sentiment][in]` does above. Pagination is keyset: pass
`meta.nextCursor` back as `cursor`, keeping `sortBy` identical for the whole traversal. It is `null` on the last
page.

### The feedback store's own path

`/v1/feedback-records` also answers on your Formbricks origin. It is the feedback store's own path, kept working
for callers pointing the [Hub TypeScript SDK](https://github.com/formbricks/hub-typescript) at a Formbricks
instance, and it forwards requests unchanged — so it speaks the store's `snake_case` contract, not this one.

It is a compatibility path and will not gain new operations. Use `/api/v3/feedback-records`.
