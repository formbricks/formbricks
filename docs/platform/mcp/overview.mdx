Formbricks ships a **Model Context Protocol (MCP) server** that lets AI assistants — Claude Code, the Claude apps, Codex, and other MCP-capable clients — work with your workspace: list and read surveys, create link surveys, update or delete them, and read or add Unify Feedback records. The agent goes through the same APIs and permission checks you use in the app, so it always respects your permissions.

You connect a client **with your own Formbricks login over OAuth 2.1** — there are no API keys to generate, copy, or paste. You approve the connection once on a consent screen, and you can revoke it at any time.

<Note>
  Prefer to use a long-lived token instead (for scripts, CI, or a client that doesn't support OAuth yet)?
  Formbricks API keys still work as a fallback — see the [MCP server technical
  handbook](/development/technical-handbook/mcp-server).
</Note>

## The MCP server URL

Point your client at your Formbricks app's `/api/mcp` endpoint:

| Instance         | MCP server URL                             |
| ---------------- | ------------------------------------------ |
| Formbricks Cloud | `https://app.formbricks.com/api/mcp`       |
| Self-hosted      | `https://<your-formbricks-domain>/api/mcp` |

## How the connection works

You don't need to understand the details to connect, but here's what happens under the hood when you add the server to a client:

1. **Discovery** — the client reads the server's OAuth metadata to find where to sign in.
2. **Registration** — the client registers itself automatically using Dynamic Client Registration (DCR). There's no client ID or secret for you to manage.
3. **Sign in & consent** — your browser opens to Formbricks. You log in (if you aren't already) and **approve** the requested access on a consent screen.
4. **Token** — the client receives a short-lived access token it sends on every request, plus a refresh token so it can stay connected without asking you to sign in again.

The whole flow uses Authorization Code + PKCE, the standard the [MCP authorization spec](https://modelcontextprotocol.io/specification/draft/basic/authorization) requires.

## What the agent can do

The MCP server exposes survey, creative, workflow, response and feedback-record tools, grouped into
authorization scopes. Read tools require the matching `:read` scope; tools that create, update, or
delete require the `:write` scope. Everything below is offered on the consent screen:

| Scope | Tools | What it allows |
| --- | --- | --- |
| `surveys:read` | `list_surveys`, `get_survey`, `validate_survey`, `get_workspace_custom_css`, `list_creatives`, `get_creative`, `show_creative`⁵, `show_survey`⁵, `get_creative_stats`, `list_tags`, `list_action_classes`, `list_contact_attribute_keys`, `get_survey_visibility`, `pull_document`⁴ | Read surveys, creatives, response tags and their counts, and surveys' custom CSS, and validate survey documents and CSS |
| `surveys:write` | `create_survey`, `patch_survey`, `edit_survey_blocks`, `set_survey_block_order`, `delete_survey`, `patch_workspace_custom_css`, `create_creative`, `patch_creative`, `delete_creative`, `duplicate_creative`, `archive_creative`, `restore_creative`, `rename_tag`, `delete_tag`, `merge_tags`, `archive_survey`, `restore_survey`, `set_survey_visibility`, `generate_survey`, `pause_creatives`, `push_document`⁴, `review_document_change`⁵ | Create, update, and delete surveys and creatives, rename, merge and delete response tags, and save a workspace's shared survey CSS — which additionally needs an organization owner or manager |
| `workflows:read` | `list_workflows`, `get_workflow`, `show_workflow`⁵, `list_workflow_runs`, `get_workflow_run`, `test_workflow`¹, `pull_document`⁴ | Read workflows and their runs |
| `workflows:write` | `create_workflow`, `patch_workflow`, `duplicate_workflow`, `delete_workflow`, `enable_workflow`, `disable_workflow`, `archive_workflow`, `unarchive_workflow`, `push_document`⁴, `review_document_change`⁵ | Create, update, and delete workflows |
| `feedbackRecords:read` | `list_feedback_datasets`, `list_feedback_records`, `count_feedback_records`, `get_feedback_record`, `search_feedback_records`, `find_similar_feedback_records`, `get_feedback_field_catalog`, `query_feedback`, `show_feedback_chart`⁵, `list_taxonomy_fields`, `get_taxonomy_state`, `get_taxonomy_run`, `get_taxonomy_record_counts`, `list_taxonomy_node_records`, `get_enrichment_status` | Read, count, search and aggregate feedback records in a workspace's feedback dataset, and read its topics |
| `feedbackRecords:write` | `create_feedback_record`, `create_feedback_records`, `update_feedback_record`², `delete_feedback_record`², `start_taxonomy_run`, `rename_taxonomy_node`, `remove_taxonomy_node` | Create, correct and delete feedback records, and build and edit the topic tree |
| `responses:read` | `list_responses`, `show_responses`⁵, `count_responses`, `get_response` | Read and count survey responses |
| `responses:write` | `validate_response`, `create_response`, `update_response`, `delete_response`, `batch_delete_responses` | Record, correct and delete survey responses |
| `contacts:read` | `list_contacts`, `count_contacts`, `get_contact`, `list_segments`, `get_segment` | Read contacts, their attributes and segments (respondent personal data) |
| `contacts:write` | `upsert_contact`, `update_contact`, `delete_contact`³, `create_contact_attribute_key`, `update_contact_attribute_key`, `delete_contact_attribute_key`, `create_segment`, `update_segment`, `delete_segment` | Create, change and delete contacts, attribute keys and segments |
| `webhooks:read` | `list_webhooks`, `get_webhook` | Read webhooks: URL, triggers and covered surveys. Signing secrets are never returned |
| `webhooks:write` | `create_webhook`³, `update_webhook`³, `delete_webhook`, `test_webhook` | Create, change and delete webhooks that send responses to other systems, and send a test delivery |
| `audit:read` | `list_audit_events` | Read the organization audit trail; organization owners and managers only. An API key needs the organization-level access-control read grant |
| `account:read` | `get_account_context` | Read who you are, your role in each organization, the organizations and workspaces you can reach, and setup facts such as workspace and survey counts. Also lets the agent list your workspaces |
| `workspaces:write` | `create_workspace`⁶, `update_workspace`⁶, `set_workspace_branding`⁶ | Create a workspace and change its name, channel, industry, brand colour and logo |
| `organizations:write` | `create_organization`⁶, `update_organization`⁶ | Create an organization and rename one you manage |
| `members:read` | `list_members`⁶ | Read the people in your organization with their email addresses and roles, and the pending invites. Personal data, so it starts unticked |
| `members:write` | `invite_member`⁶, `update_member_role`⁶, `remove_member`⁶, `resend_invite`⁶, `delete_invite`⁶ | Invite a person to your organization by email, change a member's role, remove a member, and resend or delete an invite |
| `teams:read` | `list_teams`⁶ | Read the teams in your organization and who is in them. Needs the Enterprise teams licence |
| `teams:write` | `create_team`⁶, `update_team`⁶, `delete_team`⁶ | Create, rename and delete teams, and change who is in them. Needs the Enterprise teams licence |

¹ `test_workflow` is a dry-run (no changes are saved), so it only needs the `workflows:read` scope — but because it evaluates the live workflow definition, it requires **write or manage** permission on the workspace. A read-only member will get a 403 even though the scope matches.

² Changing a record that already exists is held to a higher bar than creating one, because a feedback dataset shared across workspaces has no way to tell whose records are whose. Connected over **OAuth** (the flow on this page), both tools require you to be an **organization owner or manager**. Authenticated with an **API key** instead, they require the dataset to be assigned to a **single workspace** — a workspace-scoped key cannot be shown to own a record in a shared one — and `delete_feedback_record` additionally requires **manage** permission, matching `DELETE` elsewhere in the API. Creating, reading and searching are unaffected either way.

³ These tools also need a response scope: `delete_contact` needs `responses:write` (a contact's responses are deleted with it), and `create_webhook` and `update_webhook` need `responses:read` (a webhook delivers response data to the URL you give it). Without it the call is refused with a 403.

⁴ `pull_document` and `push_document` read and replace a survey, a creative or a workflow as one document. Surveys and creatives need the survey scope and workflows the workflow scope, so the same tool needs a different scope for each kind. A push never publishes or enables anything, and it is refused if the resource changed since you pulled it.

⁵ These tools show an interactive view in clients that support MCP Apps (see [Interactive views](#interactive-views)). Everywhere else they return their usual text and JSON. `review_document_change` needs the write scope of the document's kind and its read scope, and never writes anything itself.

⁶ Setup tools. They let an agent set up an account for you, and each needs its own scope, so approving `surveys:write` does not let an agent create workspaces or send invitations. A scope is only the first gate: the call also needs the right role. Creating or changing a workspace, renaming an organization, and inviting, listing or removing people and managing their roles and invites need an **organization owner or manager** signed in with OAuth (only an owner may invite a manager); an API key with `manage` on a workspace can change that workspace's name and branding, but never gets the member or team scopes. Creating an organization needs a signed-in person on an instance that allows more than one organization. Teams need the **Enterprise** teams licence; an owner or manager can manage any team, and a team's own admin can edit that team (but not its workspace access). `invite_member`, `update_member_role`, `remove_member`, `delete_invite`, `delete_team` and any team change that removes access do nothing until you have confirmed a preview. Leaving an organization and copying an invite link stay in the account area.

A response is someone's submitted answers, so grant `responses:read` deliberately — it is respondent
data, which `surveys:read` never exposes. An integration you connected before these scopes existed
keeps working with the access it already has. If it requests the scopes the server advertises, as MCP
clients like Claude Code do, it asks you to approve the response scopes the next time it signs in.

Scope groups are independent — a client can be granted feedback-record access without survey access, or
the other way around. `list_workspaces` is available to any read scope and to `account:read`, since every
other tool needs a workspace id. On the consent screen `account:read` and `workspaces:write` start ticked;
`organizations:write`, `members:read`, `members:write`, `teams:read` and `teams:write` start unticked, so
creating organizations, reading your colleagues' emails and roles, inviting or removing people and managing teams
are always a deliberate choice. They sit in two consent groups, "Account and setup" and "Members and teams".

<Note>
  The feedback-record tools work with **Unify Feedback** data and need the Enterprise Edition
  (`feedbackDirectories`), plus a feedback dataset assigned to the workspace. Without the entitlement or a
  directory, those tools return an authorization or validation error while the survey tools keep working.
</Note>

<Warning>
  `delete_feedback_record` permanently deletes a record — there is no undo and no trash. Grant
  `feedbackRecords:write` only to clients you want to be able to change or delete feedback, and keep read-only
  agents on `feedbackRecords:read`. Corrections via `update_feedback_record` are also irreversible — the
  previous value is kept only in the audit log.
</Warning>

Feedback records can be filtered by source, question, submission, end user, chosen option, language, date
range, and by enrichment output — sentiment, emotions and whether a record has been enriched or translated
at all. Any filter accepts several values, which are OR-ed, while different filters are AND-ed, and the
listing can be ordered by when feedback was collected or when it was stored. `count_feedback_records`
answers "how many" without fetching the records themselves — so an agent can report totals without pulling
anyone's feedback text into the conversation.

The two search tools match by meaning rather than keywords ("checkout is confusing" finds "I couldn't
figure out how to pay"), and `find_similar_feedback_records` shows how widely one piece of feedback is
echoed by others. They rely on the feedback service having an embedding model configured; on
self-hosted installs without one they report that they are unavailable. Newly created records become
searchable a short while after they arrive, and records without text are never searchable.

<Warning>
  Scopes are only a coarse gate. **Access is always bounded by your Formbricks workspace role**: even
  if a client holds a `:write` scope, a call only succeeds if you have write/manage permission on the
  target workspace — and deleting a feedback record needs manage. An agent can never do more than
  you can.
</Warning>

## Interactive views

Some tools can show an interactive view inside your agent instead of only text. Formbricks uses the
[MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) extension for this, so a client that supports it draws the view in the chat;
any other client gets the same information as plain text. Views are read-only, apart from the approval button
in the change review: changes are made by asking the agent.

| Ask your agent to... | Tool | What you see |
| --- | --- | --- |
| Create or change a survey | `create_survey`, `patch_survey` | The same survey view opens with the result, so you see what was made without asking. Block-level edits (`edit_survey_blocks`, `set_survey_block_order`) do not; ask for `show_survey` after them |
| Show or review a survey | `show_survey` | An outline of the survey (questions, logic, languages, settings) and a **Try it** tab that runs the real survey, without saving any response |
| Review a change before it is applied | `review_document_change` | What would change in a survey, creative or workflow document, with destructive changes called out, and **Approve and apply** or **Cancel** |
| Chart feedback | `show_feedback_chart` | A bar, line, area, donut, number or table chart of a feedback query, with a table view of the same data |
| Browse responses | `show_responses` | A table of responses with filters, paging and a detail panel |
| Preview a creative | `show_creative` | The creative drawn on a placeholder page, with its display status and conditions |
| Inspect a workflow | `show_workflow` | The workflow's steps as a flow and its recent runs |

Clients that render MCP Apps include Claude and Claude Desktop, ChatGPT, VS Code with GitHub Copilot, and Goose;
the [client matrix](https://modelcontextprotocol.io/extensions/client-matrix) lists the current state. Nothing
changes for a client that does not: the tools still answer, and the views never carry credentials, because every
call from a view goes back through your agent with your own connection and scopes. The survey preview loads the
survey renderer from your Formbricks address, so a client that blocks that address shows the outline only.

## Prerequisites

- A **Formbricks account** with access to the workspace whose surveys you want to work with. Read-only tasks need `read`; creating or editing surveys needs `write` or `manage`.
- The **MCP server URL** for your instance (see the table above).
- An **MCP client** that supports remote HTTP servers with OAuth — see the [setup guides](/platform/mcp/setup) for Claude Code, the Claude apps, and Codex.

<Note>
  **Self-hosting?** The OAuth provider is built in and enabled automatically — there's nothing extra to turn
  on. It just needs your instance to be served from a correct, public **HTTPS** base URL (set via `WEBAPP_URL`
  / `BETTER_AUTH_URL`). The discovery metadata and browser redirects are built from that URL, so an
  `http://localhost` or misconfigured origin will break the OAuth flow for remote clients. See the
  [self-hosting configuration](/self-hosting/configuration/environment-variables).

  Kubernetes deployments that cannot reach their own public origin can set `MCP_OAUTH_JWKS_URL` to
  the internal Formbricks `/api/auth/jwks` endpoint. This changes only the server-side key fetch;
  OAuth discovery, issuers, redirects, cookies, and audiences remain on the public URL. The standard
  path applies only when Formbricks is not mounted below a custom subpath. For an installation mounted
  at `/formbricks`, configure the complete internal URL, for example
  `http://formbricks:3000/formbricks/api/auth/jwks`.
</Note>
