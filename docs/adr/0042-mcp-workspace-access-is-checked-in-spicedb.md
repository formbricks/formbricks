# A grant's organization & workspace access is checked in SpiceDB, through `can()`

The organizations and workspaces an MCP client's grant reaches are written to SpiceDB as relationships of the grant, and for MCP calls `can()` checks the grant alongside the user (ENG-7125). Most MCP tools never receive a workspace id: they derive it from a survey, response, chart, dashboard, creative or workflow id, and several read paths skip `requireV3WorkspaceAccess`. Every decision does pass through `can()`, and SpiceDB already knows which workspace and organization each resource belongs to (ADR 0018). Checking there covers every resource type without a second resolver.

## Considered options

- **An allow-list of organization and workspace ids in the request context, checked in `can()`.** Rejected: for every resource that isn't a workspace, `can()` would have to look up its workspace outside SpiceDB, making a second evaluator that drifts from the first.

## Consequences

- With Only selected organizations, the grant relates to the organization, so workspaces created there later are reached through the hierarchy. With Only selected workspaces, it relates to each workspace. A grant with All access writes no relationships.
- A resource outside the grant is reported as not found, never as forbidden. `list_workspaces` filters through the same relationship.
- An MCP decision costs a second check, which can be bulk-checked with the user's own. Deleting a workspace or organization drops its selection rows, and the outbox drops their relationships.
- The safe direction always wins. Narrowing a grant that stays (consent re-approval, Edit) locks the grant row `FOR UPDATE`, deletes what it takes away from SpiceDB, and only then locks the consent rows and writes the new selection; if SpiceDB can't apply the delete, the request fails and nothing changes. What a save adds is written after the commit, best-effort. Revoke and every bulk end of grants commit the row delete first and remove the relationships after, best-effort, since the missing row already refuses the client (ADR 0041). In every best-effort case the outbox event the rows queued is the repair. No SpiceDB call runs while consent rows are locked `FOR UPDATE`.
- The reconciling projection reads each grant `FOR SHARE` and holds it until its SpiceDB write is done, so a reconcile that read a grant before a narrowing can't write the old relationships back after the narrowing deleted them.
- A grant left reaching nothing, because its workspaces were deleted or the user lost them, stays listed until the user edits or revokes it.
- Every resource definition answers `mcp_reach` for the grant (`authzed/schema.zed`): a workspace for its own selection and its organization's, everything below a workspace through it, and organization-level resources (teams, API keys, feedback datasets not assigned to a selected workspace) only for a grant that selects the whole organization. `can()` asks it beside the user's check in one `CheckBulkPermissions` call, and the actor's `LookupResources` lists are intersected with the grant's, two lookups whatever the count.
- The relationships are projected through the authorization outbox under the target type `mcp_grant`, keyed by grant id: triggers on `McpGrantOrganization` and `McpGrantWorkspace` queue the grant on every insert, delete or key change, and triggers on `McpGrant` queue it on a delete or an `access` change only when the grant had or gets a selection (`access` other than All access before or after), since a grant with All access holds no relationships. A narrowing is a revocation the freshness guard covers, and the backfill audits and repairs the relationships like every other projected one. A release reads only the outbox target types it knows; an event of a type it doesn't know is left pending for a release that does, never dead-lettered.
- "Not found" is applied where the MCP tool answers, not in each v3 operation, and only for what the grant doesn't reach. `can()` and the list lookups record, per tool call, when they deny on `mcp_reach` (or have nothing to check, an id that doesn't exist) and when a check confirms the grant reaches the resource. For a grant that selects organizations or workspaces, an error answer becomes one not-found body when the call was denied on the grant's reach, or when it answered forbidden or not found before any check confirmed the reach (how v3 answers an unknown id). An id outside the grant and an unknown id are indistinguishable to such a client; everything answered about a resource the grant reaches (a refusal by the user's own role, a plan refusal, a request to confirm) passes through as the operation gave it. A check that only probes a capability, such as whether the user administers the organization, runs outside this record. The REST API and All access answer as before.
