# A stored secret header value is only sent to the host it was set for

Each stored secret header value of an HTTP request step remembers the origin (scheme, host and port) of the step's URL at the moment it was set or replaced, in a `boundOrigin` column on its `WorkflowSecret` row, never in the definition (ENG-7179). The value is attached only to a request whose URL has that same origin: in a run, in a "Don't wait" delivery, in a Test run and in Send test request alike. Otherwise nothing is sent. A run fails the step with "Secret header X is set for api.example.com; enter it again for the new URL" (Continue on error still applies), Send test request answers 400, and Enable answers 422 `workflow_not_executable` until every such header has a value set for the new origin. Setting a value, inline when the draft is saved or with Replace, binds it to the step's URL at that moment; a value for a step without a valid URL is refused. The editor warns on each affected header as soon as the draft URL moves: "Enter again: the saved value is only sent to api.example.com".

This reverses the Part 2 spec (§14, "Binding secrets to the host was not adopted") and the option ADR 0058 turned down. That choice assumed only people edit a workflow's URL. Since workflows are also edited through MCP (ENG-7171), an agent with write access can change a step's URL while obeying hostile text in a survey answer, a webhook payload or an API response it read. Without binding, that one edit sends the workflow's stored API key to a server the attacker chose on the next run or test request, and the author never typed the key for it. With binding, moving a credential to a new host takes someone who has the credential and enters it again.

## Considered Options

- **Keep secrets unbound (spec §14, ADR 0058)**: no "enter it again" state when someone edits a URL, which is why it was chosen first. Rejected now because a URL edit, by an agent or a compromised session, is enough to exfiltrate every stored credential of the step, and the audit log would only show it after the fact.
- **Check only Send test request against the saved URL** (the interim fix in 640b739375): closes the one-call path but not the save-then-run one, and leaves two rules to explain. Replaced by this one rule.
- **Bind to the host only, or to the full URL**: the host alone would let a value move from `https://` to `http://` or to another port on the same name; the full URL would ask for the value again on every path change. The origin is the boundary browsers use for credentials, and it matches what the author picked when they typed the key.
- **Store the origin in the definition next to `secretId`**: one read fewer, but definitions are written by clients, copied into versions, duplicates and audit snapshots, and any of those could carry a forged origin. The row is written only by the secret store.
- **Bind a legacy value on first use**: rows stored before this change have no recorded origin. Binding them to whatever URL first uses them would let that first use be the attacker's.

## Consequences

- Rows set before this change keep `boundOrigin` null and are held to the URL of the step that uses them: the run's version in a run, the saved draft for Send test request. They bind as soon as their value is set again. Enable does not block on them, since nothing records where they were entered; Part 2 had not shipped, so few exist.
- Replace still overwrites the stored row in place (ADR 0043) while the step stays on the same origin. When the draft has moved the step to another host, the new value goes to a new row that only the draft points at, and the enabled version keeps sending its old value to its own host until the draft is enabled. The audit event for a set or replaced value names the step, the header and the new host, never the value.
- A read returns `boundOrigin` beside `isSet` for each stored secret header, so the editor and API or MCP callers can see where a value goes. A `boundOrigin` sent on write is ignored.
- Moving a step to a new API host is now: change the URL, enter each secret value again (or select Replace), then enable. Documented in `docs/workflows/http-request.mdx`.
