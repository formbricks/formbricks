# A Signature answer is a single URL string, not an array like File upload

A Signature element stores `response.data[elementId]` as one storage URL string (ENG-6810), while File upload always stores an array of URLs. Every API that returns `data` (v1, v2, v3 detail, webhooks) publishes the stored shape, and "one signature is one URL" is the cleaner contract for API users; reusing File upload's array would have been less code but would have shipped a one-item array we could never take back.

## Consequences

File upload's delete, write-validation, attachments and display code skips non-arrays on purpose: it stops a text answer holding a pasted storage URL from becoming a delete target, and a planted foreign URL from being validated as an upload. Signature therefore opts in by element id, not by shape, where the element decides what is accepted: `validateClientFileUploads` and the attachments export accept a string only for Signature element ids, and `validateSurveyAllowsUpload` allows an upload only for an upload element, `.png` only for a Signature. A write also has to name the file the upload route produces for a Signature (`signature--fid--{uuid}.png`, `fileNamePattern`) and may carry no encoded separator or dot. `uploadElementKinds` (`modules/storage/survey-upload-elements.ts`) records where the two upload element types differ (answer shape, extensions, file name, per-kind size cap), and those sites read it. Never loosen the array check for every element in those write and display paths.

Deleting is the exception, because a Signature answer outlives its element: deleting the element, or retyping it (Change question type keeps the id, so a Signature turned into Free text still holds its string), leaves the PNG under an id that is no longer a Signature. So `collectResponseFileUrls` reads a bare string under any element id, live or not, of any type, and decides by the key alone: the string is a delete candidate only when its storage key is `surveys/{thisSurvey}/elements/{theAnswerKey}/...` in the survey's workspace. A text answer can therefore only name a file under its own element id, and such a key only exists when that element once held an upload; a URL pasted into another answer, another survey's or element's key, a public key, a flat pre-#8044 key and a key with an encoded separator or dot segment are never collected. That is the same risk model as File upload arrays, where the key's scope, not the element, is what binds a delete to the survey. An earlier version of this ADR gated the bare string on the element id (a Signature, or an id the survey no longer has), which leaked the PNG of a retyped element for good; the key already proves the file belongs to this answer's element, so the gate added nothing but the leak. An array under any id is still read, so a File upload retyped to Signature has its files collected.

A cleared or replaced Signature is the respondent withdrawing it, so a write to an existing response that clears, drops or swaps a Signature's image queues the old file for deletion (`enqueueReplacedSignatureFileCleanup`), by the same key scope and only for Signature ids. It is queued in the write's transaction, so a failed write deletes nothing, and the storage delete runs in the deletion cleanup drain, not in the request. A write does not check that the object exists: a storage round trip on the public client route for every write was judged not worth it, so a hand-made value that passes the shape checks can mark a Signature as signed without an image.

Residual risks, the same as for File upload arrays. A key binds a delete or replace to the survey and element, not to one response: a respondent who knows another respondent's `signature--fid--{uuid}` URL for the same element could write it into their own answer and later clear or replace it, queueing that image for deletion. The uuid is unguessable and only the owner sees their own URL. Concurrent writes to one response can lose an update, and the cleanup of a replaced image is best effort: where a write is not transactional, a failure to queue it leaves the old image orphaned until the survey or response is deleted. The cleanup drain does not re-check that the response still references the URL when it runs.
